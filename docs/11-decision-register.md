## 5. 服务拆分的理由与代价

选择六服务是为了独立数据、安全、CPU/I/O/配额和持续任务责任；代价是接口网络故障、schema 兼容、最终一致、授权与运维。不能只展示“拆开”而不完成恢复和契约测试。

同物理数据库实例是开发成本折中，不是共享表；同一个仓库是协作方式，不是单体部署。若六服务中的某个边界造成过度耦合，可调整职责，但不能在未说明的情况下把微服务改回单体。

## 6. 风险登记

| 风险 | 触发证据 | 对策 |
| --- | --- | --- |
| 多源有入口但不许可/不可访问 | 403、验证页、附件限制、条款未清 | 不绕过，保留受阻；替换源须同类准入 |
| 多源只是大量历史资料 | 当前机会比例低 | 活跃/历史用途分报，不把历史当活跃 |
| Open/日期/金额语义混用 | 真实网页表头/章节与字段不符 | 保留范围，建立负例与人工回归 |
| 微服务变成共享库分布式单体 | 跨库、共享 ORM、同步链 | 服务账户拒绝、契约/依赖测试 |
| Redis 已发送消息丢失 | 清空/重建 broker 后消费缺口 | event_log/水位补投、超窗快照重建 |
| 索引/档案/权限最终一致 | 新版或撤权到达不齐 | 冻结输入、current/as_of、私有读当前授权 |
| 六服务+多源超出时间 | 实际工时和返工超预算 | 阶段版本、重算排期，不用空骨架凑完成 |
| HPA 放大来源/模型负载 | 429、预算增长、排队恶化 | 全局配额、背压、最高副本和停止规则 |
| “脏数据”仅人工制造 | 无真实原件与问题记录 | 自然/解析缺陷/注入分开统计 |
| 用户只要简单提醒 | B0/B1/B2 对照 | 缩 Agent 职责，保留有用的数据与跟踪 |
| 未授权资源/对外动作 | 有密钥、付费或发信需求 | 明确批准后才操作 |

不填写未经测量的概率/损失数字。
