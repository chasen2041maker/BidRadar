# 0008. v2：先做模块化单体，研究改成流水线

- 状态：已采纳，待开工
- 日期：2026-10-12

## 背景

本地版本已经跑通，但暴露出几个结构问题：

- 分层不清：`workspace/store.py` 一个类同时管校验、权限、业务规则和 SQL；数据大多以 JSON 字符串存储。
- 四个服务、各自 SQLite、回环 HTTP、手写 HTTP 层，对一个人维护的项目来说太重。
- 研究 Agent 让一次模型调用做太多事，靠越来越长的提示词规则纠错，在少量样本上过拟合。

## 决定

1. **先做模块化单体**：一份代码、两个进程（API 和 Worker）。模块之间边界清楚：每个模块只读写自己的 schema，只通过对方的公开接口调用，异步的事走 outbox 事件表。以后有需要再拆成微服务。
2. **技术栈**：FastAPI + Pydantic、SQLAlchemy 2 + Alembic、PostgreSQL。
3. **研究改成显式流水线**：解析 → 抽取要求 → 逐条匹配 → 逐条核验 → 汇总。只有追问保留工具循环。**不用 LangGraph**：它对这个场景过于自动化，不够灵活。
4. 迁移方式：新代码写在新目录，旧代码保持可运行，最后一个阶段再删。

## 为什么

- 先把边界想清楚、代码读懂，拆服务就是体力活；边界没想清楚就拆，只会得到一堆分布式的乱代码。
- 流水线的每一步都小、可单独测试和评测，出错只重做那一步；通用检查可以替代针对单个样本的补丁规则。

## 代价

- 要重写大部分基础代码，周期以周计。
- 现有的回环 HTTP 契约测试需要重写。
- 引入第三方依赖，项目不再是"只用标准库"。
