# 13｜来源矩阵与真实脏数据台账 v0.2

**Proposed｜2026-09-11。候选来源不是已接通来源；人工看过网页也不是已建清洗数据集。**

本页把“多一点数据源”和“体现清洗能力”变成可审核任务。采集和存储仍需另行授权；来源事实及链接集中在 [来源登记](12-source-register.md)。

## 1. 来源数量、格式、业务用途分别统计

一个平台的 API、XML、HTML、PDF 不算四个独立来源；同一公告的转载或翻译不算新的采购程序。香港几个部门是不同发布页面/来源，但属于同一地区生态，不宣传成几个国家的数据。

来源有三种用途：发现当前可能值得跟进的项目；关联历史发布/更正/授标；提供质量与状态识别负例。历史来源可以证明清洗能力，不能用于充实“当前可投项目”数量。

目标：R0 两种异构输入，R1 四个通过准入的来源，R3 六个通过准入的来源。R3 另有至少三个能够支持当前候选发现的来源目标；达不到则明确覆盖不足，不把历史数据改名为实时商机。

## 3. 来源准入表

每源在首次采集前填写：

```text
source_id / 发布方 / 官方入口：
用途：当前发现 / 历史关联 / 质量负例
输入：API / CSV / XML / HTML / PDF / Word / 其他
访问要求、允许频率、robots 与使用条件：
允许的保存、模型处理、展示、再分发范围：
个人信息、第三方附件与删除限制：
负责人批准的有限验证范围：
查询条件、日期窗口、分页/文件版本策略：
原生标识、修订/语言/标段关系：
预期业务字段与缺失语义：
访问/语种/附件覆盖的实际结果：
决定：可有限接入 / 仅历史 / 仅元数据 / 暂缓 / 拒绝
实际核验人、日期及证据：
```

未填不等于默认允许。公开访问、robots 允许、数据目录开放标记都不能单独替代附件版权和处理授权。不得绕过登录、验证码、付费墙或扩大允许频率。

## 4. 已观察到的三个真实语义问题

### Q-OBS-01：“Open”不是仍在招标

规划署页面的授标和取消记录均可能在 `Tender Procedure` 列写 `Open`。这是采购方式字段，不能直接映射为当前项目状态。[S16](12-source-register.md#s16)

设计验收：解析时同时保留表所属章节、表头、行内容和来源定位；处于授标/取消分节的记录不进入“当前开放项目”，金额与日期分别按授标语义处理。这是**原文语义陷阱**，不是已证实来源写错。

### Q-OBS-02：同一信息块有不同截止类型

医务卫生局网页可见资料征询截止与市场交流登记截止同处一个信息块，另有更新和关闭标注。简单取第一个日期或最后一个日期都会丢语义。[S15](12-source-register.md#s15)

设计验收：提取每个日期的类型、作用范围和原始表达；登记截止不能替代提交截止；已关闭说明与旧邀请一并保留。页面列有 PDF/Word 图标也不证明仍存在可下载附件，必须验证链接类型与响应。

### Q-OBS-03：动态模板不是空数据

BOAMP 入口在当前读取中含模板占位表达，未取得完整记录和模式。此时应标为未完成渲染/提取验证，不应把模板当真实字段或把空结果当成功同步。[S17](12-source-register.md#s17)

以上只完成页面级观察，尚无代码实现、原件冻结样本集或通过的回归测试。进入实现时需重新按许可保存可追查证据，不能用本说明代替真实测试。

## 5. 待抽样确认的问题类别

| 类别 | 需寻找的真实样本 | 规范处理 | 不能做 |
| --- | --- | --- | --- |
| 缺失/空值 | 预算未披露、没有时区、附件不可取 | 原值、缺失原因、业务未知分开 | 补零、补确定资格、猜时区 |
| 重复与转载 | 同源反复获取、不同源同一采购、不同语言 | 原件去重与业务关联分别处理 | 删除所有重复来源痕迹 |
| 版本与晚到 | 更正先到、旧公告后抓、部分标段变化 | 来源关系与字段范围控制，保留历史 | 按抓取时间全行覆盖 |
| 金额 | 不同币种、千分符、范围、税和期间 | Decimal+币种+类型+原文+作用域 | 自动换汇、全项目金额复制给各标段 |
| 文本结构 | 跨段否定、表头、脚注、HTML 实体 | 有结构解析，保留否定和证据位置 | 一条正则去掉所有格式及限制 |
| 文件/编码 | CSV 换行引号、BOM、未知编码、XML 命名空间 | 显式解析选项、错误隔离、模式版本 | 静默忽略解码错误或靠列序号硬猜 |
| PDF/Word | 提取顺序混乱、页眉页脚、扫描件 | 原生文本优先，页码定位；不可读标记 | 默认所有 PDF 是正文文本；运行宏 |
| 跨源冲突 | 日期/名称/条件不一致 | 保留来源观察，人工/规则决定版本关系 | 模型任选更有利内容当唯一真相 |

这些类别是测试设计，不代表每个站点都已经发现全部问题。没有真实实例时可用注入样本验证防御，但必须标注其来源。

## 6. 原始问题、解析器缺陷、人工注入分别记录

`natural_observation`：真实来源内存在的问题或语义复杂性，保留原件依据。

`parser_defect`：原件正常但我们的代码丢字段、误判状态或破坏表格。算实现错误，不把锅归给数据源。

`injected_case`：在允许的测试副本上有意删值、改编码、插入坏字段或打乱事件。用于确定性实验，不参与自然质量率。

`amplified_replay`：为容量测试复制或改写标识的记录。不是独立真实商机，更不是活跃用户行为。

人工裁定与模型建议分别标记。一个规则改变多条记录，要能查看处理前后、依据和误修风险。

## 7. 台账与质量报告

建议每条质量案例保存：case_id、类别、source/native ID、raw hash、观察时间、证据位置、原始值、预期规范值、规则/parser 版本、影响、实际结果、人工复核和重放方式。

每源报告总输入、成功规范化、部分解析、隔离、已知重复、不可获取等互斥结果及定义。缺失字段是业务缺口还是解析失败单列。自然异常比例以真实抽样为分母，不混入人工注入、模板空页或负载扩增数据。

清洗成果至少可展示一个完整例子：原文 → 错误风险 → 规则 → 规范结果 → 验收 → 规则升级后重放。只展示 Pandas 的 dropna/drop_duplicates 不等于完成语义清洗。

## 8. 重新处理与关联撤销

修规则后只重处理受影响 raw/version 范围；新 document_version 经事件进入 catalog。旧分析维持历史快照，最新视图标待复核，不篡改旧报告来掩盖此前错误。

误合并两个采购程序时，catalog 发布关联修订，跟踪与研究重新计算受影响范围。来源撤回、许可变化或私有数据删除的 tombstone 参与重放，不能重建时复活已撤回内容。

## 9. 非 API 路线的完成标准

至少一个真实 HTML 连接器和一个文件输入在受批准范围内完成：获取、原件留存、结构解析、质量隔离、版本化规范结果、原文引用及故障回归。网页不能只是下载标题后交给模型猜所有字段。

源不可取时可以选择同类型替代来源，但不能用 API 数据转成自制 HTML 后声称完成真实网页采集。扫描文档/OCR 不是首版硬要求；若实际资料需要，单独核验成本、准确性、敏感数据与人工复核流程。
