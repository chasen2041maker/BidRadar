# 研究 Agent

这份文档讲研究部分现在怎么工作。每一步的详细设计（喂给模型什么、检查什么、为什么这样定）见 [Agent 设计](agent-design.md)。
代码在 `bidradar/agent/`（纯逻辑）和 `bidradar/modules/research/`（任务、账本、接口）。

## 它做什么

输入一条公告（含有依据关联的更正、结果公告）、上传的招标文件和一份企业档案，输出一份研究报告：

| 部分 | 内容 | 谁写的 |
| --- | --- | --- |
| 项目事实 | 预算、最高限价、截止时间、获取文件……每行带原文 | 抽取步骤 |
| 要求对照 | 逐条要求：原文摘录、维度、状态、理由、档案依据（档案原话）、还缺什么、原文出处、核验结果 | 匹配 + 核验 |
| 待核查清单 | 从"待核查"结论的缺口和投标材料要求生成，相同的缺口合并 | 程序（不让模型写） |
| 摘要 | 按结论统计生成；可选让模型写，但其中每个数字都要在原文里找得到 | 程序 / 模型 |
| 读取范围 | 读了哪些文件、多少段；哪些章节作为模板跳过；几条结论被降级 | 程序 |

| 状态 | 含义 |
| --- | --- |
| met 满足 | 原文有明确要求，档案里有原话表明满足 |
| unmet 明确不满足 | 原文有明确要求，档案里有原话表明不满足 |
| unknown 待核查 | 缺证据、证明没核验、可能不满足但不确定，都算这一类 |
| conflicting 资料冲突 | 资料对同一件事给出了互相矛盾的说法 |
| not_applicable 不适用 | 原文明确说某个条件不适用 |

未知不当成满足，也不当成不满足。企业档案只是企业自己的声明，所以资格类要求一律待核查。

## 一次研究的过程

研究是一条**固定顺序的流水线**，不是让模型自己决定下一步（决策 0008）：

```text
① 解析     招标文件已由 documents 切好片（带页码、章节）；公告原文证据也变成片段
② 抽取     按章节分批，模型列出要求：原文摘录 + 类型（事实 / 要求）+ 维度
           摘录必须是原文的子串；不合格的带着原因重问一次；再用规则找漏掉的片段补问一次
③ 匹配     每条要求只和它的维度允许看的档案字段比较（维度表，见 agent/dimensions.py）
           → 现在是占位实现，全部待核查（练习 2）
④ 核验     逐条核验，核验时看不到别的结论：先程序检查（不花钱），再模型核验
           不通过 → 带着意见重做这一条，最多 3 次 → 仍不通过降为待核查
⑤ 汇总     排序、生成待核查清单、写摘要
```

**维度表**是这套设计的关键：旧版最典型的错误是拿"不接受连续 60 天驻场"去判"60 日内完成开发"。
现在抽取时给每条要求标一个维度，匹配时模型只看得到这个维度对应的档案字段（工期只能看人员排期，驻场只能看交付限制），想跨维度比较也拿不到材料。

**程序检查**替代了旧版提示词里的大部分补丁规则：摘录必须是原文子串；档案原话必须是所列字段的子串；理由里的数字要在原文或档案里出现；
金额角色要对得上（预算和最高限价同为 48 万也不能互相证明）；不能有联系方式；不能出现"一定中标"这类断言。

**没开模型时**走规则基线：抽取用关键词规则，匹配里需要问模型的一律待核查，核验只做程序检查。从头到尾不调模型，可以离线演示。

## 追问

追问是唯一让模型自己决定"再查什么"的地方（`agent/followup.py`）：

- 工具：`search_chunks`（找片段）、`read_chunk`（读全文）、`get_finding`（读某条结论）、`get_profile`（读档案字段）。都是只读的，只能读这次研究固定下来的材料，模型拿不到 URL、SQL、文件路径。
- 上限：最多 6 次模型调用、12 次工具调用；第 5 次起只允许回答。
- 回答要核验：引用的片段必须读过；数字要在读过的材料里出现；再由模型核验一次。不通过就只显示"基于现有材料无法确认"和缺口，不把没依据的回答给用户看。

## 费用

- 浏览和搜索不调模型。研究分两步：先预估范围和费用上限（不花钱），用户确认后才建任务（决策 0010）。
- 三层上限：全部公司合计 20 元、每家公司 10 元、每个任务 2 元。
- 每次调用前按"输入估计 + 输出上限 + 缓存全部未命中"的峰时价格**预留**，调用后按实际用量结算。
- 结果不确定（超时、断网）时，预留额照算已花，任务停在 `waiting_input`，不自动重试。
- 公开公告的抽取结果各公司共用：同样的片段、同一版规则只抽一次。

## 崩溃恢复

- 每一步的结果都存进 `research.run_steps`，步骤名精确到"一条要求的第几次匹配"。Worker 崩在第 17 条，重启后前 16 条直接复用。
- 每次模型调用有一个稳定的调用键。预留先提交再发请求，所以在任何位置崩溃，重启后都能从账本取回已经付过钱的响应，不会重复发送。
- 每一步之前检查：任务没被取消、发起人仍有分析权限、成员版本和档案版本没变、租约还在。不满足就停下，不再为过期的输入花钱。

## 评测

```bash
uv run python -m evals.run --step extract     # 抽取：召回率、精确率、维度准确率
uv run python -m evals.run --step match       # 匹配：输入用标准要求，不受抽取错误影响
uv run python -m evals.run --step verify      # 核验：故意喂错误结论，看能拦下多少、会不会误杀
uv run python -m evals.run --step all         # 端到端
```

评某一步时，它的上游一律用标准答案，这样能定位到是哪一步错了。默认用规则基线（不调模型）；
`--llm replay` 只用录下来的模型响应；`--llm live --enable-model` 才会真的调模型并录制（会花钱，先确认费用上限）。

现在有 2 个用例：一份虚构招标文件 × 2 家虚构公司，由我标注，待项目负责人复核。基线（规则抽取 + 程序核验）的核验评测：
拿别的维度的档案字段下结论、引用不存在的档案原话、编造数字，三类错误 100% 被程序检查拦下；
"档案原话是真的、结论却反了"一条也拦不下，这正是模型核验要补的部分。指标计算是练习 2 的一部分。

## v1 的教训（2026-10-01 实测）

旧版是一个工具循环 Agent：一次调用里读材料、找要求、对比企业、写理由、写摘要。在 2 条真实公告 × 2 家虚构公司上跑了 39 个任务、212 次模型调用（约 4.48 元），前几轮暴露的问题：

- 把"合同签订后 60 日内完成系统开发"当成"需要驻场 60 天"。→ 现在由维度表从结构上挡住。
- 预算和最高限价都是 48 万元，只引用了最高限价就说预算是 48 万。→ 金额角色检查。
- 借用另一条结论的原文来支持本条。→ 逐条核验，核验时看不到别的结论。
- 把"10 月 8 日至 13 日"里的"13 日"当成 13 天。→ 数字出处检查。
- 资格条件被概括时丢掉了分支。→ 摘录必须是原文子串，不允许改写。
- 反复检索撞到工具上限，没形成报告。→ 流水线顺序固定，只有追问用工具循环。
- 哪怕只有一条结论有问题，也要整份重写。→ 只重做没通过的那一条。

每个问题当时都是加一条提示词规则修掉的，换一批公告很可能遇到新问题。v2 的做法是把它们换成通用的程序检查和结构约束，对照表见 [Agent 设计](agent-design.md) 第 12 节。

## 已知短板

1. 匹配还是占位实现（练习 2），报告里的要求全部待核查。
2. 评测集只有 2 个用例，还没有人工标注；数字只能说明流程跑通，不能说明准确率。
3. 扫描件没有 OCR：读不到文字的 PDF 会被标出来，研究时用不上。
4. 真实模型还没在 v2 上跑过：第一次接入前要先用 `--llm live` 在评测集上估算费用，再定每个任务的上限（设计文档第 14 节问题 5）。
