# 研究 Agent

这份文档讲 AI 研究部分现在怎么工作、实测效果如何，以及计划怎么改。代码在 `services/research/`。

## 它做什么

输入一条公告（含有依据关联的更正、结果公告）和一份企业档案，输出一份研究报告：

- **summary**：一段业务结论，说明相关性、明确不满足的地方、最需要核查的事项。
- **findings**：逐条的采购要求。每条包含：
  - `category`：类别（技术、资格、交付、商务、预算、截止、材料、其他）
  - `requirement`：要求本身（资格类必须逐字照抄原文）
  - `status`：五种状态之一，见下表
  - `reason`：判断理由
  - `evidence_ids`：引用的原文片段
  - `profile_fields`：用到的档案字段
  - `unknown_reason`：如果是"未知"，还缺什么
- **questions**：待核查清单，由各条"未知"的缺口组成。
- **answer**：追问时的回答，非追问时为空。
- 服务器另外补上：研究范围、实际读过哪些材料、限制说明、全部引用原文。

| 状态 | 含义 |
| --- | --- |
| met | 原文有明确要求，企业档案有对应依据表明满足 |
| unmet | 原文有明确要求，企业档案明确表明不满足 |
| unknown | 缺证据、证明未核验、可能不满足但不确定，都算这一类 |
| conflicting | 资料对同一件事给出了互相矛盾的说法 |
| not_applicable | 原文明确说某个条件不适用 |

企业档案只是企业自己填的声明，资格证明没有核验过，所以**资格类要求一律是 unknown**。

## 一次研究的过程

```text
冻结输入（公告 + 档案版本）
   │
   ▼
模型选择工具 ──► search_evidence / read_evidence / get_profile_snapshot
   │  （可多轮）
   ▼
模型提交候选报告（finish_report）
   │
   ▼
程序检查 ──不通过──► 带着错误码和修改说明要求修订（最多 2 次）
   │通过
   ▼
模型语义核验 ──不通过──► 带着核验意见要求修订
   │通过
   ▼
发布报告（succeeded）
   
修订次数或调用次数用完 → 发布只列原文、全部标为待核查的保守报告（partial）
```

代码对应 `agent.py` 里 `_AgentRun` 的各个方法：`_ask_model`、`_run_next_tool`、`_check_candidate`、`_ask_reviewer`、`_read_review`、`_fail_or_revise`、`_publish`。

### 四个工具

| 工具 | 作用 |
| --- | --- |
| `search_evidence` | 按关键词和类别检索原文片段。指定类别但没命中时，返回这个类别的全部片段（原文措辞可能和关键词不同） |
| `read_evidence` | 按 ID 读取片段原文，一次最多 8 个 |
| `get_profile_snapshot` | 读取冻结的企业档案 |
| `finish_report` | 提交候选报告，必须单独调用 |

工具只能读本任务冻结的材料。模型拿不到 URL、SQL、文件路径，也读不到别的项目或别的公司。

### 上限

| 项 | 值 |
| --- | --- |
| 模型调用 | 每个任务最多 8 次（研究、核验、修订都算） |
| 工具调用 | 最多 16 次 |
| 修订 | 最多 2 次 |
| 执行时间 | 从第一次领取起 300 秒，在动作之间检查 |
| 单次输出 | 4096 tokens |
| 温度 | 0（降低随机性，但不保证每次结果相同） |

## 程序检查了什么

`evidence.py` 的 `validate_report`：

- 结构和长度符合要求。
- 每条结论都有引用，引用必须是本任务里、并且模型实际读过的片段。
- 资格类只能引用一条完整的资格原文，requirement 逐字照抄，状态只能是 unknown，理由用固定的两句话。
- met 或 unmet 必须关联非空的档案字段。
- 金额按角色检查：预算、最高限价、文件售价是三种不同的钱，每个金额都要有本条引用里同角色、同数值、同单位的原文。
- 结论、摘要、回答里出现的数字和单位，都要能在引用原文或档案里找到。
- 不能含联系方式，不能声称读完了全部标书、满足了全部资格或给出中标概率。
- 追问的回答必须由本报告里 1–3 条完整的理由拼成；待核查清单必须是各条 unknown_reason 的原文。

通过程序检查只说明"格式和引用对得上"，所以还要做一次语义核验：另一次模型调用逐条检查结论是不是真的被它引用的原文支持。

## 费用控制

`budget.py` 的费用账本单独存放在仓库外（`~/.bidradar/budgets/`），删掉业务数据也不会重置额度。

- 三层上限：本轮共 20 元、每家公司 10 元、每个任务 1 元。
- 每次调用前按"输入估计值 + 输出上限 + 缓存全部未命中"的峰时价格预留费用，调用后按实际用量结算。
- 结果不确定（超时、断网）时，预留额继续算作已花，任务停下等人处理，不自动重试。
- 实际花费超过预留额时，照实记账，并暂停整个账本。

## 崩溃恢复

- 每推进一步就保存一次进度（checkpoint）。
- 发请求前先把请求原样存下来；响应先入账、再保存进度。所以在任何位置崩溃，恢复时都能从账本取回已经付过钱的响应，不会重复发送。
- Worker 领取任务时拿到租约和递增的 epoch。租约过期被别的 Worker 接手后，旧 Worker 的写入会被拒绝。
- 每个动作前调用 `guard()`：任务没被取消、租约还在、成员权限和档案版本没变、配置没被换掉。

## 实测结果（2026-10-01）

用 DeepSeek V4 Flash（请求名 `deepseek-v4-flash`，实际响应模型 `deepseek-flash`），在 2 条真实公告（一个甘肃的 AI 项目、一个算力服务项目）和 2 家虚构公司上测试。

**总量**：39 个真实任务、212 次模型调用，按峰时价格估算约 4.48 元（其中一次网络异常的 0.16 元结果未知，按已花计）。

**前几轮暴露的真实问题**，每一轮都修了程序检查或提示词：

- 反复检索，撞到 16 次工具上限，没形成报告。
- 把"合同签订后 60 日内完成系统开发"当成"需要驻场 60 天"。
- 把"完成服务、试运行和验收"改写成"完成开发"。
- 预算和最高限价都是 48 万元，只引用了最高限价就说预算是 48 万。
- 资格条件被概括时丢掉了分支，比如"关联供应商不得共同参加同一合同"被扩大成"不能有控股关系"。
- 借用另一条结论的原文来支持本条。
- 把日期范围"10 月 8 日至 13 日"里的"13 日"当成 13 天。

**最终版本的 5 个样本**都通过了独立审查（审查者是另一个没参与实现的 AI 代理，不是人工标注）：

| 用例 | 模型/工具/修订次数 | 费用（元） | 要点 |
| --- | --- | --- | --- |
| 甘肃 × 甲公司 | 6 / 10 / 1 | 0.12 | 没把开发期限当成驻场；资格保持未知 |
| 甘肃 × 乙公司 | 5 / 10 / 0 | 0.12 | 乙公司缺研发团队，对应开发要求判为不满足 |
| 算力 × 甲公司 | 6 / 10 / 1 | 0.14 | 没把服务改写成开发 |
| 甘肃追问（浏览器） | 5 / 9 / 0 | 0.09 | 拒绝把 60 天驻场当成不适合的理由 |
| 甘肃自动复核（浏览器） | 5 / 10 / 0 | 0.10 | 档案改版后触发复核，商务细项仍未全部覆盖 |

**和规则基线对比**（14 个标签，同样由独立 AI 代理标注）：

- 甲公司：基线覆盖 7 组要求、状态全对；Agent 覆盖 6 组，漏了"获取文件的时间窗口"。
- 乙公司：基线覆盖 7 组但有 1 个状态不对（没识别出能力缺口）；Agent 覆盖 7 组、状态全对。
- 两边都没有把资格"未知"误判成满足或不满足。

**结论**：在这么小的样本上，Agent 的优势是能比较企业能力，劣势是可能漏掉基线会列出的条目。样本太少，不能说明准确率。

## 已知短板

1. **材料太少**。只有公告片段，没有完整招标文件；资格、评分、技术参数大多在招标文件里。
2. **规则在对少量样本过拟合**。上面那些问题，每个都是加一条提示词规则或程序检查修掉的。换一批公告很可能遇到新问题。
3. **一次调用做太多事**。读材料、找要求、对比企业、写理由、写摘要都在同一次调用里。
4. **只能整份报告重来**。哪怕只有一条结论有问题，修订也是整份重写。
5. **评测集太小，没有人工标注的标准答案**。

## 怎么跑一次真实评测

```bash
# 1. 启动服务，允许调用模型
python scripts/run_research_workbench.py --enable-model

# 2. 先看计划（不花钱）
python scripts/evaluate_research_case.py --notice-id <公告ID> --case-key my-case-1

# 3. 真正执行
python scripts/evaluate_research_case.py --notice-id <公告ID> --case-key my-case-1 --execute --wait-seconds 45
```

- 加 `--company 1` 用第二家虚构公司。
- 加 `--parent-run-id <任务ID> --question <问题>` 测试追问。
- 同一个 case-key 重复运行会复用原来的任务，不会再花钱；想重新测就换一个 case-key。
- 完整的输入和报告保存在 `.bidradar-data/r12-workbench/evaluations/`。
- 命令执行成功只说明流程跑通了，报告质量要另外看。
