# 17｜产品交付蓝图：先把一件业务做完整

**v0.3｜2026-09-11｜DESIGN_REVIEW。**

本页是产品设计提案。负责人已确认“前期来源可以少、项目本身优先”；具体行为与验收仍待审核。本页不宣布开始开发。

## 1. 产品定位和核心输出

使用者要解决的不是“下载全球公告”，而是：**这个项目值得我们继续核查吗；证据是什么；还不知道什么；之后有什么变化？**

BidRadar 应交付可保存、可追问、可更新的商机研究档案，不是一次性摘要。档案包含原始材料清单、条件证据表、与企业能力的比较、未决问题、人工决定和变化历史。其价值需要实际使用与基线对照证明。

## 2. 首个完整使用场景

虚构企业：做 Python 后端、知识库与 AI 应用，不接受长期驻场；资质按用户实际提供的材料确认，不预填。

| 步骤 | 使用者动作 | 产品交付 | 主要服务 |
| --- | --- | --- | --- |
| 1 | 建档并确认 | 能力、证据、偏好、版本；未知不变成事实 | workspace |
| 2 | 设置条件找项目 | 有覆盖范围和新鲜度的候选，不列已知结束项目为在招 | catalog |
| 3 | 打开项目和材料 | 标段范围、正文定位、可得与缺失附件 | catalog / processing |
| 4 | 请求分析 | 任务 ID、进度、预算状态；完成后给条件和证据 | research |
| 5 | 追问“是否需要驻场？” | 在当前标段/版本回答；找不到就保留未知和待核查来源 | research |
| 6 | 保存跟进/放弃与理由 | 人工研究决定，可修改，不代表投标资格 | tracking |
| 7 | 开启跟踪 | 关注对象、变化范围、暂停/停止控制 | tracking |
| 8 | 新资料出现后回来 | 哪条事实改变、影响哪个判断、是否待重新核查 | catalog / research / tracking |

ingestion 和 processing 为整个流程提供可追溯数据。新增来源只在上述某步因证据缺口无法完成时有优先级，不为涂满地图而增加工作。

## 3. 一份合格分析报告的契约

以下是结构提案，不是已验证的 API schema：

| 区块 | 必须解释 |
| --- | --- |
| 身份与版本 | 程序/标段、目录与文档版本、企业档案版本、分析时间、来源同步时间 |
| 分析范围 | 实际读取了哪些材料、哪些未取得、支持的语言和已知状态 |
| 简要判断 | 值得进一步核查 / 有明确冲突 / 资料待补充，并给依据 |
| 条件证据表 | 要求原文、所属标段、硬条件或偏好、企业证据、五状态、引用 |
| 未决问题 | 问题是什么、缺哪类资料、可由何种人工信息或获准工具补充 |
| 建议下一步 | 继续核查、补充资料或人工记录放弃；不自动执行投标行为 |
| 历史与费用 | 本次输入与上次差异、任务状态、用量与成本可见范围 |

来源链接能打开不代表支持结论。关键引用须回到具体原文版本与位置；证据不可获取时显示不可获取，不伪造片段。没有完整附件不能给“全部要求满足”。

## 4. Agent 的责任和边界

普通程序处理确定性过滤、日期类型、去重、权限、参数、费用与发布；Agent 决定在当前问题下查哪项证据、使用哪个已授权只读工具、怎样解释缺口。

固定查询和规则能完成的工作不强加模型。模型可提出档案修改建议，但不能直接确认资质；可提出待核查问题，但不能打开任意 URL、联系采购方或执行代码。一个主编排器足够作为首版，不预建多专家聊天系统。

研究中保持已冻结的项目/标段/档案版本。需要补充新材料时记录 manifest 变化；新输入不能悄悄改写旧报告。提问涉及另一个项目时明确切换或建立新任务，不串用证据。

## 5. 记忆不是一份越来越长的聊天记录

workspace 保存用户确认的企业事实、偏好、有效期和版本；research 保存分析、未决问题、会话和 checkpoint；tracking 保存人工跟进决定、关注和提醒。

用户说“我们可能具备某资质”只生成待确认信息；说“这个项目不适合”不能自动推导为企业永久不做该行业。用户修正档案后，旧报告标为基于旧版本，新分析单独保存。

Review decision 与 Watch 独立。建议 Review decision 取 needs_review/follow_up/dismissed，字段包括 expected_version、reason、actor 和依据引用；这属于产品提案，不是已经冻结的事件枚举。具体接口与事件在实现前补入 14 的兼容契约，不由本文偷偷变更现有事件。

## 6. 把失败状态设计成产品功能

| 情况 | 使用者看到什么 | 系统不得做什么 |
| --- | --- | --- |
| 来源失败或材料缺失 | 最近成功同步、受影响范围、未知项 | 显示为“全站无项目”或“全部已核查” |
| 请求重复、浏览器刷新 | 同一个持久任务，已有结果可继续查看 | 重复收费任务或丢失已接受请求 |
| 工具/模型超时 | 有限重试、部分结果或可解释失败 | 无限等待、伪造完成 |
| 用户取消 | 持久取消状态；新调用停止，说明在途限制 | 关闭页面就声称已取消所有外部请求 |
| 预算不足 | 明确的排队/暂停原因，旧目录与报告仍可读 | 变更成更贵模型或假装没有商机 |
| 输入版本改变 | 报告陈旧标记、变化依据、可发起复核 | 用旧报告冒充最新分析 |
| 权限撤回 | 当前私有访问拒绝，后台委托复核 | 依赖旧缓存/旧 checkpoint 继续暴露 |
| 解析规则修复 | 新派生版本、受影响报告待复核 | 修改原件来隐藏旧错误 |

UI 文案不直接创造新的任务终态。任务状态沿用领域/可靠性规范；预算暂停等可作为原因或调度状态，实际 schema 需统一审核。

## 7. 数据的最低业务要求

第一来源应提供或允许保留：稳定身份、类型/状态依据、服务范围正文、已知日期及其角色、获取时间、可定位原件，以及可说明的材料缺口。优先能找到软件/AI 相关记录；没有充分相关样本时换源或缩场景，不靠生成假公告补齐。

预算、资格、语言或更正缺失可以保留未知；稳定身份或可信原文无法建立时，不能发布自称可信的分析。真实变化样本暂缺时可使用获准历史版本作回放验证，并在验收中单列“实时同步尚未验证”。

建议先人工核查约 10 个代表项目作为种子，覆盖相关、不相关、已结束、材料不足等；随后构建 30–50 个任务案例。数量是工作量提案，不是已获取数量或固定准确率依据。少源不等于只有正常案例。

## 8. 项目交付与可选扩展

P0：档案、相关目录、可追证据、任务生命周期、条件分析、追问、保存研究与人工决定，以及必需权限和费用边界。

P1：跟踪、实质变更复核、应用内提醒、档案修正、完整网页/文件清洗例、固定评测、云端运行、备份还原、独立发布和故障验证。

P2：按需新来源、新地区、更多语种、多项目比较、外部通知、更多容量。均需明确解决的工作、代价和验收，不是为了让项目看起来大而默认加入。

相对排期见 09。微服务/Redis/K8s 从首条服务链进入，后续增加真实业务服务；不先做六个只有健康接口的容器。基础设施的每个任务都关联一个产品失败场景。

## 9. 产品验收包

| ID | 验收场景 | 必须保留的证据 |
| --- | --- | --- |
| BP01 | 首次建档后找一个相关项目 | 确认档案、查询范围、项目原文和新鲜度 |
| BP02 | 缺资质/附件仍完成有限分析 | 五状态、未知原因、没有越界结论 |
| BP03 | 追问后刷新或重登继续 | 同项目/标段/版本、已保存任务和未决问题 |
| BP04 | 保存跟进/放弃，再单独改变跟踪开关 | 修改记录、权限、版本冲突与幂等行为 |
| BP05 | 一个标段发生变化并重复投递事件 | 前后证据、只影响对应范围、唯一提醒 |
| BP06 | 取消、模型超时或预算暂停 | 实际状态、允许重试范围、在途费用记录 |
| BP07 | 修改企业事实或撤权 | 新旧档案/报告边界、拒绝旧私有访问 |
| BP08 | 与人工和规则基线比较 | 相同资料、标签、人工修改和耗时成本 |
| BP09 | 清洗真实网页或文件中的语义问题 | 原件、解析规则、前后对照和回归 |
| BP10 | 云端独立升级、故障及恢复 | 镜像/配置、日志、还原结果和环境限制 |

验收分数据回放、模拟模型、真实模型、实时同步和受控试用，不互相冒充。模拟变化能证明机制，不证明上游更新已连续观察。

## 10. 当前设计补齐与保留问题

本轮把报告交付、追问上下文、人工跟进决定、关注开关、失败体验、反馈纠错和产品验收连成一条链；原有技术细节继续按所属专题维护。

仍需审核：首用户能否接触到、第一来源是否有有用资料、哪些判断需要人工标签、角色/身份方案、模型配置、首机报价和资源、本人周工时。预算约束和产品方向已明确，不重复让用户重答；实现与采购未授权。

最终证明是“本人写了关键逻辑，使用者完成了核查，错误被识别并修复，系统在预算内运行”，不是“来源数量最多”。
