# 01｜BidRadar 项目计划书 v0.2.1

**状态：DESIGN_REVIEW｜2026-09-11｜微服务、多源全球覆盖与低预算云部署修订稿。**

本稿描述目标系统，不表示已经实现。用户已明确微服务、Redis、K8s、多源脏数据、排期、全球来源和阿里云方向；月度总预算约人民币 100–200 元。具体实现、分配和购买仍待审核。原来源见 [12](12-source-register.md)，新增核验和预算见 [16](16-global-sources-cloud-budget.md)；样本数/性能/工时都是提案。

## 1. 产品目的

帮助软件与 AI 服务团队，从公开采购信息中发现值得进一步核查的项目，读懂要求、比较企业能力、保存证据和未决问题，并持续跟踪变化。

直白地说：**帮公司找可能接的活，减少错读要求、漏掉变更和反复查资料。**使用者负责参与资格确认和是否投标；系统不预测中标、不自动投标或联系采购方。

产品价值尚待用户验证。公开数据和微服务架构的存在不自动证明有人需要；需比较人工、规则与 Agent 流程的审核成本和遗漏情况。

## 2. 为什么这个业务适合微服务

这是本项目的设计判断：来源抓取是外部 I/O，文件解析有 CPU/内存和安全风险，目录检索偏读，Agent 调用耗时且受配额限制，跟踪任务有定时和去重语义，企业档案有私有权限。它们适合不同的发布、扩容和故障策略。

因此不再采用 v0.1 的单体路线。建议六个有数据所有权的服务，而不是每个接口一个服务，也不是仅把同一应用复制到六个容器。服务独立镜像/配置/迁移/契约；通信通过 API 和版本化事件。

## 3. 最新硬约束

| 要求 | 本计划怎样兑现 |
| --- | --- |
| 独立完整项目 | 不使用公司代码、数据、提示词或账号，个人负责从数据到运行 |
| 规模可增长 | 六服务目标结构，分源接入，读写与长任务分离，容量梯度 |
| 微服务从开始设计 | 先写服务边界、数据所有权、事件和故障；首个运行阶段就跨服务 |
| Redis 从开始纳入 | Streams 事件、缓存、全局配额有具体职责；数据库保留业务与重放依据 |
| K8s 从开始纳入 | 首个服务阶段验证部署、DNS、身份、探针、网络与资源，而非尾部补 YAML |
| 数据向全球扩展 | 提议六个地理大区的代表性来源验证；8–12 个候选入口池，逐源准入，不承诺全量实时 |
| 体现脏数据清洗 | 原始保留、规范化、质量隔离、规则版本、回放、前后对照和真实问题台账 |
| 阿里云线上部署 | 低并发单节点方案先评估，保留独立服务和后续扩容路径 |
| 总预算约 100–200 元/月 | 费用包含计算、存储、网络、备份与模型；200 元规划上限不等于购买授权 |
| 有排期 | 相对周、容量假设、依赖、验收、风险缓冲与个人责任 |
| 不急着开工 | 本轮仍只写文档，阶段启动另行明确授权 |

## 4. 目标用户与真实业务边界

建议首用户为需要查看海外采购信息的软件/AI 服务团队的业务人员，以及协助核查要求的技术人员。不假设用户具有某国实体、资质或跨境参与资格。

系统分别展示业务相关性、已识别硬条件、企业证据、缺失资料及参与资格未知项。面向一个软件场景逐步接入多个市场，不同时扩成全行业 CRM、报价或采购法律平台。

英语可用内容作为首批分析范围；其他语种可先归档与结构化索引，明确不支持语义判断。新增中文、西班牙语等分析必须各有人工核验样本，不能把多源直接宣传成全语种支持。来源地域与标的履约地域分别保存。

## 5. 端到端业务流程

企业档案经用户确认 → 数据采集与留存 → 文件解析和质量隔离 → 程序/标段/版本关联 → 规则和检索筛选 → Agent 有限补证 → 要求/证据/能力逐项比较 → 人工决定跟进 → 变化后重新检查并提醒。

虚构例子：企业不接受驻场；某标段明确要求现场交付，就展示冲突及原文；文件没说，则保留未知。新更正只影响一个标段时，不能把其他标段日期也改掉。

## 6. 六个服务的目标职责

| 服务 | 业务责任 | 主要数据所有权 |
| --- | --- | --- |
| ingestion | 来源连接器、调度、增量抓取、原件登记 | source/sync/raw_asset/outbox |
| processing | 安全解析、规范化、质量检查、隔离与重处理 | document_version/evidence/quality_issue/parse_run |
| catalog | 程序与标段身份、版本投影、商机目录、检索索引 | procedure/lot/notice_relation/catalog_revision/search_projection |
| workspace | 身份映射、团队权限、确认的企业能力和偏好 | workspace/membership/profile_revision/preference |
| research | Agent、上下文、条件抽取与匹配、分析快照和报告 | analysis_run/finding/checkpoint/result |
| tracking | 收藏、变化关联、复核流程、应用内提醒 | watch/reassessment/notification |

详细所有权、API 和事件见 [架构](04-system-architecture.md) 与 [契约](14-service-event-contracts.md)。前端网关不另算业务域；公共模型访问先由 research 的适配器负责，不自建万能模型平台。增加国家不增加同样多的微服务，首先扩展 ingestion 的来源适配器与 processing 的规则包。

## 7. 数据路线

v0.2 的 TED、CanadaBuys、香港 GLD、医务卫生局、规划署、BOAMP 和英国候选保留，但不再作为固定全球终点。新增美国 SAM、厄瓜多尔 SERCOP、南非 eTenders、澳洲 AusTender 等代表性候选；其中 API、历史下载和网页各有用途。

本轮已读 SAM 接口说明、SERCOP 下载/API 说明、南非公开网页、AusTender API 说明与部分原有来源。SAM 需 Key；澳洲已核实的 API 面向合同公告，不当活跃投标清单；南非旧 API 路径返回 404；CanadaBuys 重读遇到 403。详细状态、智利身份门槛等见 [16](16-global-sources-cloud-budget.md)。没有实际运行连接器。

数据形式和站点数量分别计数；同平台不同文件格式不算新来源。历史资料用于清洗、关联和负例，不能放进当前商机列表。聚合目录是发现和归档入口，不等于已独立实现其所有发布者接入。

每源单独通过访问、使用条件、字段语义、重放与业务适用审核。网站开放访问不等于可任意转载附件；受阻时保留状态，不绕过访问控制。[数据基础](03-data-foundation.md)

## 8. 交付层次，不用“大”代替可用

| 层次 | 必须交付 | 不代表 |
| --- | --- | --- |
| D0 设计稿 | 服务、数据、事件、排期、风险、全球范围与预算 | 已批准实施 |
| R0 基础链 | 两种输入经 ingestion→processing→catalog；Redis 通信、K8s 运行、可查证据 | 六服务全部完成 |
| R1 可用研究 | 四个准入来源的阶段目标，企业档案、检索、Agent、工作台 | 全球覆盖或商业价值已验证 |
| R2 完整跟踪 | 六服务、持续同步、记忆、变化复核、幂等提醒、恢复与隔离 | 生产级高可用 |
| R3 扩展验证 | 向六大区代表性接入扩展；逐地区报告真实样本、活跃/历史、语种与缺口 | 六大区全部能提供实时可投项目 |

R3 的数量和时间仍待审核。每增加一源必须有字段映射、真实问题、有限同步和使用边界证据；不为涂满地图增加未经验证的来源。容量/故障/受控试用/英文交接继续保留，不能把全部时间改成扩源。

## 9. Redis、K8s、数据库与云环境

Redis Streams 为跨服务事件通道；各服务数据库记录业务事务、Outbox/Inbox 和可重放事件。Redis 不是唯一任务账本，传输 ACK 不等于最终结果。缓存 Redis 与事件/配额 Redis 分实例，避免缓存淘汰误删事件。

开发与低成本云环境可共用一个 PostgreSQL 实例，但每服务独立数据库/角色/迁移，禁止跨库查询、共享事务和直读别人的业务表。它们共享故障域，不能称数据库高可用。Catalog 搜索投影可重建，不是企业档案权威副本。

首个可运行阶段纳入 K8s。云平台方向为阿里云，ECS + K3s 是预算方案提案，不是已选套餐。先评估 4 vCPU/8 GiB 低负载布局；16 GiB 仅在真实报价和总预算允许时考虑。CPU/内存数字不是已经测得的最低需求。

真实网页大文件解析、索引构建与 Agent 任务错峰、限并发；模型只分析经过筛选或人工选择的少量项目。控制总费用，不让 HPA 自动买机器。报价/网络/模型地域/使用条件/域名部署要求/备份验证通过后才批准线上部署。

## 10. 正确性不变量

公告、程序、标段、语言与更正分开；原始事实、用户确认能力、模型推断分开；未知/冲突/解析失败不强行转成满足/不满足。

所有结论有输入版本和证据定位；新输入不改写旧报告。跨服务没有假定的原子事务，发布、取消、重试和提醒都能解释。私有资料在 HTTP、事件、索引、缓存、日志、checkpoint、导出中都受同一权限约束。

## 11. 排期与个人实现

原基准为 **28 个有效项目周，每周 12–15 小时，约 336–420 小时容量**，不是已确认可用工时或保证日期。第 7/13/17 周分别是原基础链、档案检索、Agent 研究的阶段目标，均须实际验收。

全球扩源复用原数据阶段，但不假定新增加的身份申请、语种、规则和连接器全部没有成本。先完成三大区的可用数据链，再于扩展阶段逐项验证南美/非洲/大洋洲；不通过就明确延期该覆盖，不牺牲 Agent 评测和恢复验收来凑数量。相对排期增量见 [16](16-global-sources-cloud-budget.md)，原详细责任见 [09](09-roadmap-ownership.md)。

本人亲手完成代表性连接器、清洗规则、契约、事务、Agent/记忆、事件恢复、K8s 排障及负载解释。AI 辅助重复页面、测试设计和审查，不能把核心全部代写后当个人掌握。

## 12. 验收与停止条件

保留人工、规则、Agent 三种基线。数据质量按来源/格式/字段/语种报告；自然脏数据、故障注入、放大回放分别标记；性能报告环境、负载、P95、错误率、积压和成本。

无证据引用、误把授标当在招、跨租户泄露、旧 Worker 覆盖、重复提醒、无法重放的消息丢失为阻断问题。报价超过总预算、网络无法满足已选来源、实际内存无法容纳基础链时，先重审运行方案，不直接购买后要求追加费用。费用告警不等于厂商硬停机上限，应用侧须保守限制可变调用。

来源许可或材料不足时缩该来源覆盖；Agent 无收益时缩模型职责，不取消有用的数据产品。不报未经测量的改善百分比或薪资结果。

## 13. 明确不做

自动投标/报价、联系人营销抓取、法律资格裁定、任意网站/代码执行、全行业全语种、移动端、模型训练平台、服务网格和多云平台均非本轮目标。全球来源不是全球部署；不默认购买多地域节点、托管数据库和 GPU。

当前成果仍是计划，不启动采集、部署或编码；下一步是负责人审核方案。
