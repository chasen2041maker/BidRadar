# 01｜BidRadar 项目计划书 v0.2

**状态：DESIGN_REVIEW｜2026-09-11｜微服务与多源数据修订稿。**

本稿描述目标系统，不表示已经实现。用户已明确微服务、Redis、K8s、多源脏数据和排期要求；具体实现方案仍待审核。外部事实见 [来源登记](12-source-register.md)，样本数/性能/工时都是提案。

## 1. 产品目的

帮助软件与 AI 服务团队，从公开采购信息中发现值得进一步核查的项目，读懂要求、比较企业能力、保存证据和未决问题，并持续跟踪变化。

直白地说：**帮公司找可能接的活，减少错读要求、漏掉变更和反复查资料。**使用者负责参与资格确认和是否投标；系统不预测中标、不自动投标或联系采购方。

产品价值尚待用户验证。公开数据和微服务架构的存在不自动证明有人需要；需比较人工、规则与 Agent 流程的审核成本和遗漏情况。

## 2. 为什么这个业务适合微服务

这是本项目的设计判断：来源抓取是外部 I/O，文件解析有 CPU/内存和安全风险，目录检索偏读，Agent 调用耗时且受配额限制，跟踪任务有定时和去重语义，企业档案有私有权限。它们适合不同的发布、扩容和故障策略。

因此不再采用 v0.1 的单体路线。建议六个有数据所有权的服务，而不是每个接口一个服务，也不是仅把同一应用复制到六个容器。服务独立镜像/配置/迁移/契约；通信通过 API 和版本化事件。

## 3. 最新硬约束

| 要求 | 本计划怎样兑现 |
| --- | --- |
| 独立完整项目 | 不使用公司代码、数据、提示词或账号，个人负责从数据到运行 |
| 规模可增长 | 六服务目标结构，分源接入，读写与长任务分离，容量梯度 |
| 微服务从开始设计 | 先写服务边界、数据所有权、事件和故障；首个运行阶段就跨服务 |
| Redis 从开始纳入 | Streams 事件、缓存、全局配额有具体职责；数据库保留业务与重放依据 |
| K8s 从开始纳入 | 首个服务阶段验证部署、DNS、身份、探针、网络与资源，而非尾部补 YAML |
| 数据不能少 | 六个主候选源、补充源；先两种异构输入，再四源稳定、六源扩展 |
| 体现脏数据清洗 | 原始保留、规范化、质量隔离、规则版本、回放、前后对照和真实问题台账 |
| 有排期 | 相对周、容量假设、依赖、验收、风险缓冲与个人责任 |
| 不急着开工 | 本轮仍只写文档，阶段启动另行明确授权 |

## 4. 目标用户与真实业务边界

建议首用户为需要查看海外采购信息的软件/AI 服务团队的业务人员，以及协助核查要求的技术人员。不假设用户具有某国实体、资质或跨境参与资格。

系统分别展示业务相关性、已识别硬条件、企业证据、缺失资料及参与资格未知项。面向一个软件场景逐步接入多个市场，不同时扩成全行业 CRM、报价或采购法律平台。

英语可用内容作为首批分析范围；其他语种可先归档与结构化索引，明确不支持语义判断。后续法语/中文必须各有评测，不能把多源直接宣传成全语种支持。

## 5. 端到端业务流程

企业档案经用户确认 → 数据采集与留存 → 文件解析和质量隔离 → 程序/标段/版本关联 → 规则和检索筛选 → Agent 有限补证 → 要求/证据/能力逐项比较 → 人工决定跟进 → 变化后重新检查并提醒。

虚构例子：企业不接受驻场；某标段明确要求现场交付，就展示冲突及原文；文件没说，则保留未知。新更正只影响一个标段时，不能把其他标段日期也改掉。

## 6. 六个服务的目标职责

| 服务 | 业务责任 | 主要数据所有权 |
| --- | --- | --- |
| ingestion | 来源连接器、调度、增量抓取、原件登记 | source/sync/raw_asset/outbox |
| processing | 安全解析、规范化、质量检查、隔离与重处理 | document_version/evidence/quality_issue/parse_run |
| catalog | 程序与标段身份、版本投影、商机目录、检索索引 | procedure/lot/notice_relation/catalog_revision/search_projection |
| workspace | 身份映射、团队权限、确认的企业能力和偏好 | workspace/membership/profile_revision/preference |
| research | Agent、上下文、条件抽取与匹配、分析快照和报告 | analysis_run/finding/checkpoint/result |
| tracking | 收藏、变化关联、复核流程、应用内提醒 | watch/reassessment/notification |

详细所有权、API 和事件见 [架构](04-system-architecture.md) 与 [契约](14-service-event-contracts.md)。前端网关不另算业务域；公共模型访问先由 research 的适配器负责，不自建万能模型平台。

## 7. 数据路线

主候选：TED（API/XML）、CanadaBuys（CSV/数据字典）、香港 GLD（公开 XML 列表）、香港医务卫生局（HTML/文件链接）、香港规划署（HTML 授标/取消表）、BOAMP（数据/API 入口，待完整验证）。英国 Contracts Finder / Find a Tender 作为现行覆盖仍待核验的补充。

这些是候选，不是已连接清单。数据形式和站点数量分别计数；同平台不同文件格式不算新来源。历史资料用于清洗、关联和负例，不能放进当前商机列表。至少两种真实异构输入从早期进入，不把脏数据等到最后。

最大风险是入口存在但原文、许可或所需字段不足。每源单独通过访问、使用条件、字段语义、重放与业务适用审核。网站开放访问不等于可任意转载附件；受阻时保留状态，不绕过访问控制。[数据基础](03-data-foundation.md)

## 8. 交付层次，不用“大”代替可用

| 层次 | 必须交付 | 不代表 |
| --- | --- | --- |
| D0 设计稿 | 服务、数据、事件、排期、风险与验收 | 已批准实施 |
| R0 基础链 | 两种输入经 ingestion→processing→catalog；Redis 通信、K8s 运行、可查证据 | 六服务全部完成 |
| R1 可用研究 | 至少四个准入来源，企业档案、检索、Agent、简单工作台 | 全市场或商业价值已验证 |
| R2 完整跟踪 | 六服务、持续同步、记忆、变化复核、幂等提醒、恢复与隔离 | 生产级高可用 |
| R3 扩展验证 | 六个准入来源、容量与故障实验、受控试用、英文交接 | 自动满足岗位年限或薪资 |

范围增大体现在独立来源、持续工作、版本历史、租户隔离、恢复和可测容量，不是服务数量无限增加。

## 9. Redis、K8s 和数据库

Redis Streams 为跨服务事件通道；各服务数据库记录业务事务、Outbox/Inbox 和可重放事件。Redis 不是唯一任务账本，传输 ACK 不等于最终结果。缓存 Redis 与事件/配额 Redis 分实例，避免缓存淘汰误删事件。

开发阶段可共用一个 PostgreSQL 实例，但每服务独立数据库/角色/迁移，禁止跨库查询、共享事务和直读别人的业务表。Catalog 的搜索投影可重建，不能成为企业档案的权威副本。

首个可运行阶段在本地 K8s 验证服务网络、身份、配置、资源、持久卷和观测。Compose 仅为开发辅助。后续压测扩容在自有测试环境使用回放/模拟，不拿政府站点和真实模型供应商当压力靶场。

## 10. 正确性不变量

公告、程序、标段、语言与更正分开；原始事实、用户确认能力、模型推断分开；未知/冲突/解析失败不强行转成满足/不满足。

所有结论有输入版本和证据定位；新输入不改写旧报告。跨服务没有假定的原子事务，发布、取消、重试和提醒都能解释。私有资料在 HTTP、事件、索引、缓存、日志、checkpoint、导出中都受同一权限约束。

## 11. 排期与个人实现

基准排期为 **28 个有效项目周，每周 12–15 小时，约 336–420 小时容量**，不是承诺或已经确认的可用工时。开始日期待负责人确定。每阶段包含测试与返工，详见 [排期](09-roadmap-ownership.md)。工时下降时按剩余工作量重算，不删掉微服务/多源等已确认目标冒充完成。

第 7 周目标是第一条跨服务数据链，第 13 周目标是可看可查的档案与检索，第 17 周目标是可演示 Agent 研究；完整扩展与压测在后段。每个目标须以实际验收为准。

本人必须亲手完成代表性连接器、清洗规则、服务契约、数据库事务、Agent 工具和记忆、事件恢复、一次 K8s 排障及压测解释。AI 辅助重复页面、测试设计和审查，不能把核心实现全部代写后当个人掌握。

## 12. 验收与停止条件

保留人工、规则、Agent 三种基线。数据质量按来源/格式/字段报告；自然脏数据、人工故障注入、放大回放分别标记；性能必须同时给环境、负载、P95、错误率、积压和成本。

无证据引用、误把授标当在招、跨租户泄露、旧 Worker 覆盖、重复内部提醒、消息丢失且无法重放是阻断问题。来源许可或材料完整性不足时先缩该来源覆盖；Agent 无收益时缩模型职责，而不是取消整个数据产品。

## 13. 明确不做

自动投标/报价、联系人营销抓取、法律资格裁定、任意网站/代码执行、全行业全语种、移动端、模型训练平台、服务网格和多云平台均非本轮目标。Kafka/MCP/独立模型网关等只在有明确需求和新决策后进入。

当前成果仍是计划，不启动采集、部署或编码；下一步是负责人审核方案。
