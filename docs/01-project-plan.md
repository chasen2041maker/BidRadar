# 01｜BidRadar 项目计划书

**版本：v0.1｜状态：待审核设计稿｜日期：2026-09-11**

本计划描述目标系统，不代表已实现。现阶段只讨论与审核，暂不写业务代码、不建基础设施。官方事实和未核验项统一列于 [来源登记](12-source-register.md)；下文架构、范围和阈值属于设计建议。

## 1. 一句话目的

帮助软件与 AI 服务团队，从公开采购公告中发现值得进一步核查的项目，理解要求、识别能力缺口，并持续跟踪变化。

直白地说：**帮公司找可能接到的活，并减少读错要求、漏看变更和反复查资料的工作。**

用户仍负责判断是否投标及实际参与。系统不是中标预测器、法律资格认证系统或自动投标机器人。

## 2. 为什么做这个产品

产品假设：业务人员在“发现项目→阅读要求→比对能力→追踪变化”之间有重复劳动，尤其容易丢失来源、遗漏未决条件和混淆历史版本。BidRadar 尝试把这些环节连成一个可复查的流程。

这些痛点尚未通过目标用户访谈确认。不能因为有公开数据、能运行模型，就认定已找到商业需求。立项后需比较人工方法与简单关键词/规则基线；若固定脚本更省事，应缩小 Agent 的职责，而不是人为增加复杂度。

工程目标：由项目负责人独立负责数据获取、清洗、领域建模、Agent 编排、记忆、数据库、任务执行、测试与部署；AI 参与方案和审查，不替代本人实现关键逻辑。项目产出应能接受代码、数据、故障和设计追问，而不是仅展示技术栈。

## 3. 目标用户及限制

首用户建议限定为有明确软件/AI 服务能力、需要查看海外公开采购信息的业务人员或小型团队。首版先验证“信息筛选与跟踪”价值，不承诺替中国公司找到可直接投标的欧盟项目。

参与资格、地域限制、联合体或分包可能性需要具体文件及人工确认。未取得证据时保留未知；不把技术匹配转换成法律资格结论。

首版分析可明确支持英语可用的公告内容；保存其他原文并标明语言覆盖，不声称覆盖整个欧洲或全部行业。中文界面与辅助说明不等于中文译文可替代原始要求。

## 4. 完整业务闭环

```text
用户确认企业能力与筛选偏好
              ↓
读取真实公开公告，记录来源与抓取时间
              ↓
保存原文 → 清洗字段 → 关联采购程序、标段与公告版本
              ↓
规则筛选候选 → 检索证据 → Agent 补充理解
              ↓
展示要求、对应能力、明确冲突、未知项及原文位置
              ↓
用户收藏/放弃/补充信息，决定是否跟进
              ↓
后续公告和时间变化触发复核 → 应用内提醒
```

例子均为虚构说明：用户表示会做 Python 后端和知识库、不接受长期驻场；某标段明确要求驻场时展示对应冲突，未说明驻场时标为未知。不能把“未说明”直接筛掉，也不能说它支持远程。

## 5. 产品交付范围

| 能力 | 预期成果 | 边界 |
| --- | --- | --- |
| 商机发现 | 可筛选、去重、带新鲜度的公告/标段列表 | 不宣称找全所有机会 |
| 要求分析 | 每项要求有原文依据、作用范围和判断状态 | 文件不全时不得给“完全满足”结论 |
| 企业能力记忆 | 用户确认、可修正、版本化的能力与偏好 | 不从聊天推断公司有某资质 |
| 商机档案 | 历史分析、收藏原因、未决问题、人工备注 | 不作为完整 CRM |
| 持续跟踪 | 日期、范围、条件与状态变化的说明 | 不自动联系采购方或提交材料 |
| 可运行系统 | 可恢复任务、权限、安全、成本与质量证据 | 受控部署不包装成生产规模 |

## 6. 第一条可用业务链与完整 v1 的区别

**第一条业务链**仅需一个来源、一份经确认的企业档案、少量真实公告、一个证据详情页和人工触发分析。它用于尽早验证数据与输出，不要求先具备所有基础设施。

**完整 v1**再加入持续同步、版本跟踪、持久记忆、应用内提醒、多 Worker 故障处理、缓存、受控部署和评测。Redis、Kubernetes 属于后续工程交付目标，不是第一条链的开工前置条件。

第一轮样本建议：100 条公开公告作数据检查，其中人工核查至少 10 条原文；后续评测拟用 50 个有标签的案例。数量只是预算和验收提案，未抓取、未标注、未测得。见 [评测与验收](08-evaluation-acceptance.md)。

## 7. 数据路线和最大前提

首个候选源为 TED Search API。官方文档说明该接口可访问已发布公告、不要求身份认证，并提供 `POST /v3/notices/search`。[S1](12-source-register.md#s1)

这只证明官方存在公开入口，不能证明本机可访问、字段足够完整、所有附件可下载、所有数据可按任意方式重新分发。实际拉取、源字段映射、语种/附件覆盖与条款复核仍未完成。当前对法律声明页面的读取遇到访问验证，不能用历史对话代替最新完整审阅。[S2](12-source-register.md#s2)

采集优先级为官方接口、允许直接下载的原文、逐域审核的公开附件；不绕过登录或访问控制。源失效时保留最后同步时间并标注陈旧，不声称“目前没有新商机”。

若真实样本不足以支持筛选，先缩小国家/语种/公告范围或评估另一合法公开源，再审计划，不悄悄用模拟数据冒充真实数据。

## 8. 架构主张

建议采用模块化单体：一个 Python 代码库，API、采集 Worker、分析 Worker 分进程运行；前端只做业务工作台。模块通过明确的应用接口合作，不起步拆十几个服务。

PostgreSQL 保存结构化业务状态、任务和证据关联；原始文件放可控文件/对象存储；检索从结构化查询和全文检索起步，再用评测决定向量检索的收益。候选向量存储为 pgvector。

Agent 在受约束工作流中选择工具和补充证据；程序掌管权限、预算、状态和结果发布。短期图状态不能代替企业档案和业务数据库。

阶段演进：数据库持久任务 → 经故障验证的多 Worker → 有收益的 Redis 缓存/可选任务传输 → Docker 与 CI → 受控 Kubernetes。各层复杂性都有对应业务问题和验收条件。详见 [架构](04-system-architecture.md)。

## 9. 五条不可牺牲的正确性要求

1. 公告、采购程序、标段和版本分开建模；不因标题相似自动合并，也不因多语言重复而重复计算商机。
2. 未知、冲突、过期、未获取与不满足分别表达；缺失值不变成零或肯定答案。
3. 结论关联原文版本、位置、企业档案版本及分析配置；能解释“当时为什么这样判断”。
4. 用户私有能力与笔记不能通过检索、缓存、日志或 Agent 状态泄露给其他用户。
5. 任务允许重试，发布结果和应用内提醒必须去重；旧执行不能覆盖新结果。

## 10. 成功怎么判断

| 维度 | 要回答的问题 | 证据 |
| --- | --- | --- |
| 数据 | 原始资料能否可靠获取并正确关联？ | 样本、清洗记录、版本测试 |
| 业务 | 输出是否比简单基线减少人工工作？ | 配对案例、审核用时、采纳与纠正记录 |
| Agent | 是否在需要时补查证据，缺资料时会停止？ | 工具轨迹、未决项、预算与失败分类 |
| 工程 | 重复、宕机、取消、越权时行为是否正确？ | 可重复执行的故障与权限测试 |
| 学习 | 本人能否独立修改一层并验证影响？ | 个人提交、调试记录、解释与代码审查 |

不预写提升百分比、中标率、线上用户数或薪资结果。没有人工标签时不报“准确率”；没有真实用户反馈时不称商业价值已验证。

## 11. 范围排除

不做自动投标、自动报价、采购方群发联系、联系人采集营销、资格法律裁定、全行业全语种覆盖、任意网站爬取、移动端、通用多 Agent 平台、模型训练平台或多云运维平台。

MCP、额外模型框架、外部邮件、第二数据源等均后置：有真实集成需求且经单独审核再增加。不为 JD 关键词而硬加服务。

## 12. 个人职责与推进方式

本人负责每层第一条实际链路：一个连接器、一套清洗与版本入库、一个有证据的分析、一个安全的记忆更新、一个可恢复任务、一次部署排障。AI 可审查和解释，不包办全部实现。

采用里程碑与关口，不以日历逼迫开工。当前里程碑是设计审核；后续需明确授权数据验证，再进入小任务实现。每个任务保留输入、预期、失败场景、实际测试和未解决问题。

## 13. 主要风险与停止条件

数据可得不代表资料完整；技术匹配不代表可参与；英语范围可能太小；使用者可能并不需要 Agent；输出可能漏读关键条件；基础设施可能挤占业务时间。对应验证与缩减方案见 [决策登记](11-decision-register.md)。

出现资料使用边界不清、核心字段无法稳定解析、无可解释引用、跨用户泄露或没有可用的实际筛选场景时，不进入开放试用。先补证据或缩小范围，而不是给未完成系统贴“生产级”标签。
