# 09｜产品优先的排期与个人责任 v0.3

**Proposed｜2026-09-11。明确排期是用户要求，周数与工时仍为审核用估计，不是开工授权或保证。**

## 1. 容量与范围

保留 28 个有效项目周、每周 12–15 小时、总计约 336–420 小时的原容量假设。每周约 20% 的时间用于测试、文档和返工，包含在该容量中；最后阶段留收尾空间。开始日期、实际工时和开发效率均未确认，每两周按实际完成与剩余工作量调整。

本轮取消“先扩四源再做 Agent”“完成全球扩源才交付”的关键路径。相同容量优先投入研究、记忆、跟踪、评测与运行。少源不是保证更快交付；来源审批、服务契约和个人学习仍可能增加工时。

如果每周只有 8 或 10 小时，按剩余工作量重算，不暗删微服务、Redis/K8s、关键安全或恢复；可以先交阶段版本。Week 1 在负责人确认对应阶段后计，不是当前自动开始计时。

## 2. 当前主排期

| 相对周 | 产品成果 | 工程成果与本人重点 | 阶段验收 |
| --- | --- | --- | --- |
| W1–2 | 审核一个用户流程、报告契约和种子案例；获授权后验证一个主来源 | 领域/服务边界、事件、成本、首数据准入；本人核查原文和失败语义 | D0/G0–G2；不默认采购或实现 |
| W3–5 | 有真实项目和可定位原文的目录 | ingestion→processing→catalog；独立镜像/分库角色、Redis、K8s、幂等与基本恢复；本人写接收/清洗/提交链 | R0：一个有用输入足够，不要求先凑两种格式 |
| W6–8 | 建立确认档案，列表/筛选/详情、证据和材料缺口可查 | workspace 权限、版本、结构化/全文基线、前端业务流程；本人写 SQL 与授权测试 | 可手工完成一次核查，使用两个测试空间验证隔离 |
| W9–12 | 条件分析、多轮追问、保存报告和人工决定 | research 工具/上下文/预算/持久任务；tracking 最小决定接口；30–50 任务案例逐步形成，真实模型小批验证 | R1：可用研究；不以四源为条件，完成一次具体误判修复 |
| W13–16 | 收藏、变化对比、复核、应用内提醒；档案修正与停止跟踪 | tracking 持久流程、命令终态、唯一提醒、取消/撤权；本人写状态与本地事务 | R2：完整持续流程；历史回放和真实变化分别记录 |
| W17–20 | 补齐当前业务需要的网页/文件清洗、纠错和使用者反馈 | 事件日志重放、乱序、旧 Worker fencing、缓存失效、独立升级和契约 CI | 完整 v1 质量与恢复；仅有实质缺口时补第二来源，不按数量验收 |
| W21–24 | 经批准的阿里云低负载试用、成本/数据健康可见 | 资源账、Terraform 候选、Helm/Kustomize 二选一、HTTPS/身份/密钥、部署/回滚/独立备份和还原 | R3 运行部分；总预算内真实报价和资源通过后才能采购 |
| W25–28 | 配对评测、反馈修复、文档和英文演示 | 资源允许的负载/故障实验、可重现改进、运行手册与真实贡献 | R3 收口；未过项保留未完成，全球不阻塞 |
| R4 后续按需 | 新来源、地区、语种或更大容量 | 根据真实需求/测得瓶颈估算与批准 | 独立扩展，不含在默认 28 周承诺中 |

表格是主投入位置，不是“到后段才做测试/权限/成本”。相关功能进入时就有测试、CI、授权和预算；后段补深度与交付证明。首次云端部署可在前置关口通过后提前，但不能未经报价和授权创建资源。

## 3. Redis/K8s 进入时间

基础设计期间明确边界，首个跨服务业务链（本稿 W3–5 提案）即验证 Redis 和 K8s。只部署已有业务服务，不批量创建空容器。随后增加实际业务服务、恢复、网络、配额、扩容和备份。

单节点证明服务部署和特定故障，不证明多节点高可用。真实网站和模型供应商不是压力靶场；高负载用自有获准环境和明确标记的回放/模拟。

## 4. 关键依赖

真实原文先于可信分析；workspace 授权先于私有研究；目录/证据版本先于报告；报告契约与变化语义先于跟踪复核；预算先于计费调用；协议先于跨服务发布。

R1 的人工决定由 tracking 最小接口保存，R2 扩展 watch/notification，不暂存在别的服务然后偷偷共享表。该新增契约在实现前按 14 做兼容审核。

可以用显著标 mock 的数据开发前端契约，但阶段验收必须接真实后端与获准样本。一个人同一时间最多一个核心实现任务，另搭一个轻量文档/核验任务，不同时打开六个半成品分支。

## 5. 本人必须亲写和验证

| 能力 | 代表性成果 | AI 可协助 |
| --- | --- | --- |
| 采集/清洗 | 一个实际连接器；后续真实 HTML 和文件处理、质量隔离及回放 | 来源说明、规则审查、异常样例设计 |
| Python/SQL | 有界并发、超时取消、参数化查询、事务、迁移、索引 | 解释、审查、定位提示 |
| 微服务通信 | Outbox→Streams→Inbox→job；重复/丢失/乱序与恢复 | 契约草案、故障走查 |
| Agent/记忆 | 工具选择、上下文、证据、五状态、checkpoint与发布 | 评测设计、有限示例 |
| 产品状态 | 保存决定、跟踪开关、档案修正、任务恢复和权限 | 交互与验收审查 |
| 运行 | 缓存失效、费用限额、日志追踪、部署、回滚与还原 | 模板比较、报告反馈 |
| 效果 | 人工/规则/Agent 同案例对照，一次实际错误修复 | 查标签问题、分析结果 |

不按代码行数声明贡献。能独立改一项需求、运行测试、解释影响，才计个人掌握。旧项目只迁移自己理解的方法，不复制公司数据或源码。

## 6. 单任务模板

```text
任务 / 产品行为 / 里程碑 / 所属服务：
目标与知识点：
输入、输出、API/事件/数据库副作用：
本人实现范围与 AI 辅助范围：
失败场景、禁止结果、预算边界：
验收、测试与实际证据：
实际工时、阻塞、剩余估计：完成后填写
```

代码审查沿用结论、正确项、问题风险、改进、下一任务五段。未请求完整实现时不交付整套代码代替本人练习。

## 7. 扩源和延期规则

新增来源先回答：哪个用户任务做不成，现有源是否真的缺证据，原始附件能否解决，新增的使用/维护/语言/费用成本是什么。无明确收益则保留候选，不安排当前开发。

可后移全球覆盖、第二及更多来源（无缺口时）、更多语种、精致界面、多项目比较、外部邮件和额外容量。真实网页/文件质量证据属于完整交付，不能永久取消；可在核心研究之后完成。

不能以扩源延后 Agent、吞掉测试与个人实践，也不能因预算低改回共享表或取消恢复。报价不合适先重审，不默认追加钱。每阶段只按实际验收记完成，不靠周数自动晋级。

## 8. 可展示成果

R0 可讲真实清洗与事务；R1 可展示核查与追问；R2 可展示持续使用及最终一致；R3 提供云端、费用、质量和恢复证据。全球扩展是之后的新增成果，不是作品有用的前提。

英文材料讲清一个使用场景、一个误判、一项恢复和一个取舍。来源数量、模拟用户、计划成本不写成已达到的生产成绩。本轮仍只做设计审核。
