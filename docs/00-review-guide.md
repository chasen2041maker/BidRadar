## 2. 阅读顺序

**第一遍只审“做什么”。**读 [计划书](01-project-plan.md) 和 [产品范围](02-product-scope.md)。应能不用技术词解释使用者、输入、输出和不做的事。

**第二遍审“数据与业务对象”。**读 [数据基础](03-data-foundation.md) 和 [领域模型](05-domain-model.md)。重点是公告、采购程序、标段、版本、未知及冲突。

**第三遍审“系统如何协作”。**读 [架构](04-system-architecture.md) 和 [Agent/记忆/匹配](06-agent-memory-matching.md)。重点不是框架名，而是哪一层负责事实、规则、决策、权限和副作用。

**第四遍审“失败与验收”。**读 [可靠性与安全](07-reliability-security-operations.md)、[评测](08-evaluation-acceptance.md) 和 [路线](09-roadmap-ownership.md)。最后用 [决策登记](11-decision-register.md) 收口。

## 3. 五个设计关口

| 关口 | 审核问题 | 通过依据 | 当前状态 |
| --- | --- | --- | --- |
| G0 产品范围 | 帮谁完成哪一项工作？边界是否足够小？ | 负责人确认首用户、场景、非目标和成功定义 | 待审核 |
| G1 数据可行性 | 真实公告和证据能拿到多少？使用范围是否清楚？ | 授权后的样本报告、字段映射、条款复核、不可获取清单 | 待验证 |
| G2 模型与架构 | 更新、未知、权限、任务恢复能否解释一致？ | 实例走查、数据关系、状态转换、替代方案决策 | 待审核 |
| G3 质量与运行预算 | 怎么判断系统好于简单基线？哪些错误阻止试用？ | 标签规范、留出集规则、阻断测试、费用上限 | 待审核 |
| G4 实施授权 | 第一个任务由谁写、如何验证？ | 负责人明确批准一个阶段/任务并记录范围 | 未授权 |

G1 可以先以人工查阅公开样本推进；需脚本或 API 验证时另行授权。G2 的初稿可先审，但最终物理字段和取值映射不能先于真实样本定死。

## 4. 审架构时用同一个实例走查

使用虚构的“某机构采购知识检索系统，含两个标段”作为结构示例：

1. 一条公告涉及两个标段，系统是否错误地产生两个完全独立程序？
2. 其中一个标段要求现场交付，但另一个没有说明，是否错误继承成两个都要求驻场？
3. 企业档案没有相关资质记录，系统是否错误判定不具备资质？
4. 后来一份变更只修改一个标段的日期，是否保留旧证据且只更新受影响结论？
5. 同一变更重复导入、分析 Worker 中断重启，是否重复提醒？
6. 用户撤销资料授权后，旧缓存、图状态、报告下载是否还会泄露资料？

任何一步解释不清楚，先修设计，不用增加框架掩盖问题。

## 5. 反馈格式

复制下列模板到审核记录或讨论，不需一次评价全部文档：

```text
审核对象：文档 + 章节 / 决策 ID
结论：接受 / 要修改 / 需要证据 / 暂缓
问题场景：具体输入、已有状态、发生的变化
担心的结果：可能误判、遗漏、重复、越权或成本失控
建议：保留、缩小、替换或移到后期
所需证据：样本、测试、用户反馈或官方说明
审核人及日期：实际填写，不由 AI 代签
```

## 6. 当前最应审核的六项

| 决策 | 建议起点 | 为何现在值得审 |
| --- | --- | --- |
| 首用户 | 已有软件服务能力、需要看海外公开采购机会的团队 | 不能假设任何初创都能参加任何采购 |
| 分析粒度 | 标段优先；无可靠标段关系时保留未知 | 避免金额、资格、日期串用 |
| 材料边界 | 公告优先，附件按访问与使用许可补充 | 公告并不保证包含所有条件 |
| 判断形式 | 条件证据表 + 未决项 + 可解释排序 | 不把模型评分冒充资格结论 |
| 初始后台任务 | PostgreSQL 持久任务；Redis 后置 | 先掌握正确性，避免两个任务真相来源 |
| 第一提醒渠道 | 应用内提醒 | 先证明更新价值，再承担外部邮件投递风险 |

审核不以“所有技术都听说过”为完成标准，而以负责人能够解释一个正常路径和一个失败路径为标准。完成审核仍不代表系统已实现。
