## 3. 审核关口

| 关口 | 通过所需材料 | 当前 |
| --- | --- | --- |
| G0 产品 | 首用户、典型工作、非目标与价值验证方式获确认 | 待审核 |
| G1 多源数据 | 每源访问/许可/格式/覆盖报告；至少两种真实输入走查 | 待授权验证 |
| G2 服务与数据 | 六服务所有权、禁止跨库、事件版本、乱序与快照案例 | 待审核 |
| G3 运行 | Redis 丢消息恢复、鉴权、K8s 网络策略、预算和压测隔离 | 待审核 |
| G4 排期与开工 | 可投入工时、阶段范围、明确授权单个任务 | 未授权 |

不要求所有来源都验证完才批准第一个小样本实验；但某来源未过准入不得悄悄对外展示其数据。架构可先定逻辑边界，物理字段必须跟随实际样本。

## 4. 用同一个实例走查跨服务链

虚构例子：某软件项目两标段，两个来源转载，其中一份更正只改标段 B 的截止时间。

1. ingestion 重复获取一份文件，processing 能否识别原件相同但保留获取记录？
2. processing 按两个网页标题产生不同名称，catalog 是否错误合并两个不相关项目？
3. catalog 发布变更时，tracking 和 research 是否各自收到，而不是同消费组互相抢消息？
4. research 冻结旧版本后新更正到来，报告是历史结果、陈旧结果还是可以叫最新？
5. Redis 重启丢失已投递消息，怎样从服务事件日志补回，而不是只重发未发送 Outbox？
6. workspace 撤销成员权限，旧 Token、缓存、checkpoint 和导出能否继续泄露？
7. processing 扩到多个 Pod，来源请求量和模型费率是否也失控？
8. 任一服务单独升级，其事件和 API 是否兼容上一版本消费者？

每一步应指出事实所属服务、事务边界、失败状态和测试，而不是回答“框架会处理”。

## 6. 本轮优先审五个决定

六服务边界是否合适；数据库角色隔离和事件重放是否讲得清；首批选择哪两种输入；28 周容量是否匹配实际工时；哪些性能指标要在拿到基线后冻结。

不再讨论是否“允许”微服务，也不把大项目缩回单脚本。讨论的是怎样把已确认方向做成能维护、能证明的工程。
