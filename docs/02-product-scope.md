# 02｜产品范围与业务契约

状态：Proposed / 待审核。以下均是产品设计，不是已验证的市场结论。

## 1. 使用者与工作边界

主要角色：软件/AI 服务公司的业务人员，负责初筛公开项目并组织进一步核查。辅助角色：确认公司能力的负责人、补充技术判断的工程师。首版按一个工作空间管理团队；多角色复杂审批不作为首条业务链前置条件。

系统协助“找、读、比、记、追踪”。用户负责采购规则理解、实际资格确认、报价、合作安排和投标行动。不能默认用户有欧盟实体、特定认证或跨境参与资格。

## 2. 术语表

| 词 | 本项目内的含义 |
| --- | --- |
| 采购方 | 发布采购需求的一方 |
| 公告 Notice | 某次发布的信息载体；可能不是新的招标机会 |
| 采购程序 Procedure | 系统用于关联一项采购过程的业务对象，关联须有依据 |
| 标段 Lot | 可具有独立范围、金额、条件、截止时间的分析单元 |
| 版本/更正 | 信息的演变，须保存关联与原始依据 |
| 商机 Opportunity | 针对某工作空间、某分析单元值得继续核查的业务视图；不是官方资格或中标结论 |
| 跟踪 Watch | 用户选择关注后续变化的设置 |
| 证据 Evidence | 可定位到具体原文版本和作用范围的支持内容 |

这些是内部概念定义。实际官方字段和公告类型映射须用真实样本与官方模式核验，不直接照术语表生成迁移。[数据基础](03-data-foundation.md)

## 3. 五个核心用户故事

| ID | 用户希望 | 系统必须 | 失败时 |
| --- | --- | --- | --- |
| U1 | 保存公司的能力和偏好 | 用户确认后形成新版本；区分事实与偏好 | 冲突或未确认值不得覆盖原事实 |
| U2 | 找到可能相关的项目 | 给出筛选条件、范围、新鲜度和原始来源 | 来源异常时展示同步失败，而不是空结果冒充无商机 |
| U3 | 看懂项目是否值得跟进 | 要求、证据、对应能力、明确冲突和未知逐项展示 | 文件缺失/语种不支持时保留缺口 |
| U4 | 记住看过哪些项目 | 收藏、放弃理由、人工笔记、待核实问题可回看 | 保存失败不显示“已保存” |
| U5 | 知道收藏项目发生变化 | 显示变更前后、影响范围和上次分析是否陈旧 | 不能建立可靠版本关系时进入待确认，不伪造差异 |

## 4. 页面职责，不先做复杂聊天首页

**商机列表**：筛选与排序、项目/标段信息、资料更新时间、已知状态、未知数量、收藏。不能只放一个由模型生成的百分制分数。

**商机详情**：公告原文链接、要求证据表、企业能力匹配、未知/冲突、来源覆盖范围、版本时间线、跟进动作。侧边追问只在这个明确上下文内进行。

**企业档案**：确认能力、案例和资质；偏好独立管理；每次修改可审计，过期项提示重新确认。

**跟踪中心**：关注项目、未决项、变更、应用内提醒、已读状态。无实质变化不重复产生提醒。

**任务与数据状态**：同步和分析任务进度、失败类别、可重试/待人工原因、成本与时间。内部诊断信息按角色显示，不把密钥或全文提示词暴露给所有用户。

## 5. 匹配结果的对外措辞

一个结论至少含分析对象、截止信息、证据范围、企业档案版本、清晰理由和未决项。

允许：

- “与已确认的软件服务能力相关，值得进一步核查。”
- “公告明确要求现场交付，与已确认的不驻场偏好冲突。”
- “尚未取得资格附件，不能判断相关条件是否满足。”

不允许：“有 87% 中标率”“你们确定有资格”“没写驻场所以支持远程”“预算未披露所以为 0”“文件获取失败但全部要求已检查”。

偏好冲突与资格冲突使用不同标签。用户可放宽偏好，但不能通过调整排序权重把明确硬条件不满足改成满足。

## 6. 跟踪的事件范围

首版关注四类事件：明确的截止时间变化、业务范围/技术要求变化、资格或必备材料变化、已知程序/标段状态变化。第五类为临近已知截止时间的定时提醒，必须绑定具体截止类型和版本。

公告晚到、乱序和重复导入都可能发生。依据已核验的来源关系与时间语义更新，不以抓取顺序当官方生效顺序。项目截至某次同步的已知状态，与真实世界当前状态分开展示。

应用内提醒先行。外部邮件是后续独立决策，需要用户订阅、接收地址确认、取消机制和投递状态；本计划不替用户发送任何消息。

## 7. 首版范围建议

TED 单源；软件/AI 服务子集；明确支持英语可用内容；采购程序/标段范围内的证据分析；一个受控工作空间先验证，再通过隔离测试进入邀请试用。

历史案例可用于实验，但已结束项目不能混入“当前可跟进”列表。分析范围不保证全市场覆盖，所有列表显示筛选范围与最近成功同步时间。

## 8. 价值验证，而不是假设一定有用户

在有限验证阶段，用真实公告和经同意的企业能力档案，让 2–3 位潜在使用者比较人工读公告、规则筛选和 BidRadar 结果。人数是招募目标，不是现有资源。

记录每人保留/放弃原因、是否误漏硬条件、要补哪些材料、审核耗时，以及是否愿意再次用。公开报告只发获同意且脱敏的数据。

找不到使用者时可先以真实资料做自用研究，但要明确“缺用户价值验证”，不能用虚构企业案例冒充真实采纳。

## 9. 产品退出/缩减规则

若只有公告摘要有用，先减少对话与复杂记忆；若附加资料普遍不可取，聚焦发现与信息缺口提示；若某语种/类型无法可靠分析，明确排除并报告覆盖率；若 Agent 不优于固定流程，保留可靠流程而不是强迫所有步骤智能化。
