# 02｜产品范围与业务契约 v0.2

**Proposed｜2026-09-11。微服务、多源和早期 Redis/K8s 是已确认方向；本页具体产品切分待审核。**

## 1. 用户与非目标

主要用户为软件/AI 服务团队负责找项目和初筛要求的业务人员；技术人员补充能力核查，负责人确认资质、案例和团队偏好。系统协助找、读、比、记、追踪，不替用户判断法律资格、提交投标或自动联系采购方。

不默认任何用户拥有某国实体、特定认证或当地交付能力。可技术匹配但参与资格未知，两者分开展示。

## 2. 业务对象

| 对象 | 内部定义 |
| --- | --- |
| Notice 公告 | 一次发布信息，不必然是新商机 |
| Procedure 程序 | 有明确来源依据关联的一项采购过程 |
| Lot 标段 | 有独立范围、日期或条件的分析单元 |
| Document version | 某份原文与某次解析，不用最新网页覆盖历史 |
| Opportunity 商机 | 面向企业的可核查业务视图，不是中标概率 |
| Evidence 证据 | 原文版本、位置、范围与允许访问条件 |
| Watch 跟踪 | 用户订阅后续变化的业务设置 |

这些是内部模型，不是所有数据源通用字段。源语义映射见数据文档。

## 3. 用户故事与验收

| ID | 用户工作 | 必须交付 | 失败时 |
| --- | --- | --- | --- |
| U1 | 登记企业能力 | 人工确认、版本、有效期、偏好独立 | 未确认推测不覆盖事实 |
| U2 | 找项目 | 多源列表、过滤范围、重复关联、同步时间 | 来源失败不冒充没有项目 |
| U3 | 核查适合度 | 要求—原文—能力—状态—缺口 | 文件不足不得称全条件满足 |
| U4 | 继续研究 | 历史报告、提问、笔记、放弃理由 | 保存失败不显示已保存 |
| U5 | 跟踪变化 | 前后差异、影响标段、复核和提醒 | 关系不明就待确认，不捏造版本链 |
| U6 | 查看数据健康 | 来源新鲜度、解析失败、隔离原因、覆盖限制 | 不向普通用户暴露私有诊断内容 |

## 4. 六个页面职责

商机列表用于筛选，不靠一个黑盒总分；详情展示要求表、证据、版本、未知与冲突；企业档案管理确认事实与偏好；研究面板在具体项目上下文内追问；跟踪中心管理收藏、变化、已读；数据健康页向适当角色显示来源和处理质量。

不先做聊天首页来掩盖目录、证据和数据链缺失。界面明确区分当前候选、前期意向、历史授标、取消/结束以及状态未知。状态取自语义与证据，不把网页上的 Open 一律理解为仍开放。

## 5. 输入覆盖与多源交付

R0 用两种异构真实输入验证主链；R1 至少四个准入来源；R3 目标六个，其中保留直接 HTML 采集和原始文件处理路径。多个来源可以有重复转载，必须记录，不把数量机械相加成独立商机数。

当前可跟进来源与历史/质量来源分别统计。至少三个经过验证的当前候选来源是扩展目标；未达到时如实标注范围。来源某条资料可读不等于它的所有附件可读。

首批分析英语可用内容。其他语种可留存和索引，不自动承诺能正确分析；翻译永远引用原文并记录版本。法语/中文启用必须单独评测。数据来源多不代表扩大到所有采购行业。

## 6. 输出措辞

允许：与已确认能力相关；存在某项明确冲突；附件未取得、条件待核查；截至某次同步所知。

禁止：保证有资格；中标概率 87%；没写驻场所以远程；金额缺失所以零预算；抓取失败但全部要求已检查。

硬条件与软偏好分开。用户可修改偏好，但提高排序权重不能消除不满足或未知的硬条件。

## 7. 变化和通知

跟踪截止、范围、条件、状态及临期提醒。日期类型和标段明确后才安排精确倒计时；时区未知不编造 UTC。以业务版本和明确来源关系为准，不按到达顺序覆盖。

第一通知渠道是应用内提醒。外部邮件将来单独审核订阅、取消、收件人和投递不确定性，本轮不发送。

## 8. 用户验证

拟邀请 2–3 位潜在使用者比较原始页面、规则筛选和 Agent；这是目标，不是已有用户。用相同输入记录审核耗时、遗漏硬条件、需要补证和再次使用意愿。公开反馈须同意并脱敏。

找不到使用者时保留自用/研究验证标记。可以缩某项语义功能，不能把历史数据当活跃项目或用合成用户伪造商业价值。
