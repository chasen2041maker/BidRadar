# 15｜Kubernetes 初始设计、扩容与容量验证 v0.2

**Proposed｜2026-09-11。用户已要求从初期纳入 K8s/Redis 并后续加压；本页的配置、数字和环境均未批准或实测。**

## 1. 进入时间与目标

W1–2 完成运行边界设计，W5–7 第一条真实数据链就部署到本地 K8s，验证 ingestion→Redis→processing→catalog；其余服务随业务里程碑加入。不是项目末尾补 YAML，也不是现在生成六个空容器。

Compose 是可选开发辅助，不替代 K8s 验收。早期本地单节点环境用于学习发布/网络/恢复；后续多节点或受控云环境验证另一组故障，不把单机多 Pod 写成多节点高可用。

## 2. 工作负载布局提案

| 工作负载 | 初始形态 | 扩展依据 |
| --- | --- | --- |
| Web/网关 | 独立 Deployment/Service，按路由进入业务服务 | 请求率与延迟，网关不承接领域事务 |
| ingestion | 调度/接收入口与抓取 Worker 可分 Deployment，同一业务服务 | 每源积压、外部配额与连接上限 |
| processing | 有界 API + 解析 Worker，独立资源/身份 | CPU、内存、文档长度、队列年龄；重型解析可用受控 Job |
| catalog | 查询 API 与索引/事件 Worker 分运行 | 查询延迟、索引滞后、DB/索引能力 |
| workspace | 权限/档案 API + 必要事件 relay | 授权可用性、响应延迟；不能为扩容降低鉴权 |
| research | 接受/查询 API + Agent Worker | 排队、模型配额、费用、长任务状态 |
| tracking | 关注/提醒 API + 变化/定时 Worker | 变化扇出、到期任务年龄与去重成本 |

一个服务内多个 Deployment 用于扩缩不同执行面，不因此宣称新增了几个微服务。定时触发入口只提交幂等任务，不把所有数据库状态藏进某个 Pod 的内存时钟。

## 3. 数据与基础设施

开发阶段一个 PG 实例可含六个服务数据库，独立角色/迁移；同实例共享故障域，后续按瓶颈拆资源。不能凭微服务之名先自建六套高可用数据库。

redis-core 与 redis-cache 是两个实例/进程，不是换 logical DB：前者有事件/配额的持久化、noeviction 和背压；后者可淘汰、可重建。[S19](12-source-register.md#s19) 持久卷不是备份，AOF 也不替代本项目 event_log 重放。

对象存储按所有者/敏感级别分区，访问通过受限凭据或拥有者授权下载。原文、解析产物、索引、日志、备份分别计量和保留。云厂商、托管产品、节点规格和费用都需后续明确决策。

用户机器规格未知，先记录可分给集群的 CPU/RAM/磁盘。若不足以同时运行全部服务，可在不同阶段组合运行、移出重型观测或选择经批准环境；不声称有限本机资源能完成全部容量目标。

## 4. 从第一服务开始的部署契约

每服务有独立锁定依赖、镜像/不可变 digest、配置、ServiceAccount、密钥范围、Deployment/Service、资源 requests/limits、健康/就绪/启动检查与优雅退出。

liveness 只判断进程内部生命状态，不因外部网站或模型暂时故障反复重启；readiness 按该入口能否安全接新请求/任务定义。Worker drain 时停止领取，正在执行的任务完成或等待租约接管，termination 宽限需与任务策略一致。

首版禁止默认 privileged、共享所有密钥、把数据库公开互联网或挂载主机管理套接字。镜像最小权限、只读根文件系统等在兼容性确认后验证，而不是只贴配置不运行。

所有部署区分 startup、可接受任务、依赖降级和已失败。服务注册使用 K8s DNS，不自建一套冗余注册中心。

## 5. 网络和身份必须实测

默认拒绝网络，再允许必要服务、DNS、数据库、Redis 和受控出口。所选 CNI 必须真正实现 NetworkPolicy，实际测试允许/拒绝连接；只有 YAML 没有效果不算通过。[S22](12-source-register.md#s22)

允许网络不等于业务授权。HTTP/事件生产者需验证工作负载身份、issuer/audience/期限，用户或后台委托另验。具体身份机制待审，不强制上服务网格。

ingestion 只访问获批来源；processing 无任意公网访问或模型密钥；research 只访问批准模型出口与服务 API。域名/重定向/IP 安全另由受控采集器验证，NetworkPolicy 本身不能代替 URL 级 SSRF 防护。

## 6. CI/CD 和独立发布

每服务构建、静态检查、单元/集成/契约测试和镜像扫描独立可运行；文档变更不触发付费部署。真实源/模型测试手动、限量、预算隔离；不可信 PR 无密钥。

schema 变更采用 expand→迁移消费者/数据→contract，测试 N/N-1 契约。回滚旧镜像不能自动撤销破坏性迁移；每次发布有恢复和数据兼容说明。

演练独立升级一个服务，其余继续提供有限服务；记录错误率、消息滞后和恢复。一次性部署六服务成功不代表能独立演进。

## 7. 容量梯度：数字是输入提案，不是吞吐承诺

| 档位 | 目录规模提案 | 交互压力提案 | Agent/后台压力 | 用途 |
| --- | --- | --- | --- | --- |
| L0 | 1,000 条目录记录 | 10 个虚拟用户 | 1–2 个并行模拟分析任务 | 基础链与故障可复现 |
| L1 | 10,000 条 | 25 个虚拟用户 | 2–5 个并行模拟任务 | 索引、缓存和服务边界 |
| L2 | 100,000 条 | 100 个虚拟用户 | 10–20 个并行模拟任务 | 积压、资源和扩容瓶颈 |
| L3 条件扩展 | 1,000,000 条 | 300 个虚拟用户 | 按模型模拟和硬件另定 | L2 验收、成本批准后再审，不是首版完成条件 |

一条目录记录、一个采购程序、一个文档和一个文本块不是同一计数。用原始样本放大产生的记录必须标 amplified_replay，不报独立真实商机数。10 个虚拟用户不等于 10 RPS，更不等于 10 个真实活跃用户。

另做固定到达率查询实验，如 10→50→100 请求/秒的候选输入，在每阶段记录实际完成吞吐、延迟、超时和排队；不把表中虚拟用户数与 RPS 混成同一个参数。可达目标由基线/硬件决定，未达到是实验结果而非需要隐藏的问题。

## 8. 三条压力轨道分开

**查询轨道**：列表、过滤、分页、详情、全文/向量检索。固定数据和请求分布，比较冷/暖缓存，记录 P50/P95/P99、错误率、DB 连接/慢查询、缓存命中和索引版本。首先测可复现的小样本，再增长。

**数据轨道**：使用已许可冻结 API 响应、HTML、CSV/XML 和文件，按文档字节数/页数/格式分桶。分别测抓取回放、解析、质量隔离、事件和索引吞吐，报告 docs/min、MB/min、队列年龄与内存。不能只用很短的文本冒充复杂 PDF 清洗性能。

**研究轨道**：用固定延迟、流式输出、429、超时、错误 JSON 的模型模拟器测试编排/队列/预算/取消。小批真实模型实验单独用人工标签测质量、费用与延迟，不能把模拟吞吐当真实模型服务能力。

高负载仅访问自有/获明确授权的测试服务。政府网站和真实模型供应商不作为无限压力靶场；真实来源调用只按许可与配额做有限验证。

## 9. 压力场景与判定

先稳定运行和基线，再阶梯增加、短时突发、持续运行及恢复。候选时长可用 5 分钟预热、15 分钟稳态和单独 60 分钟持续实验，实际时长按资源/预算批准并写报告；小样本分位数不能宣传稳定 SLA。

性能阈值在 L0 基线和业务需求后冻结。可讨论普通读取 P95≤1 秒、接受异步任务 P95≤500ms 等候选目标，但在负责人确认环境前不作为承诺或已达标值。复杂检索、原文下载、任务等待与模型执行分别定义，不用一个延迟指标混包。

硬性正确性先验收：受测重复/丢消息不静默丢任务，旧代次不能提交，内部提醒不重复，权限不泄露。429/背压作为预期保护行为单列，同时报告总拒绝比例，不能从错误分母中偷偷删除不利结果。

## 10. 扩容策略与停止规则

处理 CPU 的 parsing Worker 可以基于 CPU/内存和积压调整；研究 Worker 主要看可执行任务队列年龄、全局模型配额和预算，不单靠 CPU。HPA 的指标来源、资源 requests 和采样需实际验证；队列指标适配器或 KEDA 是否采用是后续选型，不当已安装能力。[S21](12-source-register.md#s21)

先比较固定 1→2→4 副本，再启用自动扩容，记录吞吐是否改善、瓶颈是否转移，不能假定线性增长。scale-down 保留稳定窗口和 drain；最大副本受 DB 连接预算、对象存储、Redis、来源和模型总配额共同限制。

扩容前计算每服务 pool_size×副本数和数据库可用连接；队列堆积因模型 429 时先背压，不加更多副本重试。redis-core 或费用账本不可用时暂停受限外部调用，不能绕过全局限流。

成本上限触发、持续 OOM、事件日志接近保留界限、授权异常、磁盘不足或源限流恶化时停止升压，保留证据并恢复。压测过程不能关闭正确性检查来凑高数字。

## 11. 故障和恢复实验

计划覆盖：Pod 中途终止、parser OOM、大文档超时、Redis 重启/清空已发送消息、消费组重建、DB 短暂不可用、错误 NetworkPolicy、模型 429、workspace 暂不可用、取消与提交并发、单服务兼容升级、备份还原。

每个实验写预期、注入范围、停止条件、实际日志/指标/状态和恢复步骤。跨库备份恢复后对账孤立引用/版本/撤回和重复提醒；不能只看到 PostgreSQL 启动就说恢复完整。

## 12. 费用与最终证据

成本按计算资源+数据库/Redis+对象与备份存储+网络+观测+模型/向量分别计；调用价格与服务未选择，不编月费。单任务、日、月和压测上限必须经批准；不自动购买集群、升级套餐或发模型请求。

最终报告记录代码/镜像/契约版本、硬件、节点数、副本、数据与文件分布、冷暖缓存、负载模型、实际时长、成功/失败/拒绝、P95、积压、丢重记录、费用及未覆盖项。

当前本页只是规划。下一步先审数据量口径、初始环境、Redis 恢复和扩容边界，再决定具体实验。
