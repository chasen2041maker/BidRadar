# 15｜Kubernetes、受控交付与容量验证 v0.3

**Proposed｜2026-09-11。微服务、早期 Redis/K8s、阿里云和总预算方向已确认；资源和性能未实测。**

## 1. 初期进入，不以基础设施阻塞产品

按 [09](09-roadmap-ownership.md) 当前排期，首个 ingestion→processing→catalog 业务链就验证Redis和K8s，后续随档案、研究、跟踪加入真实服务。不先生成六个空应用，也不把K8s拖到最后。

本地集群用于早期测试，云端目标是经批准的阿里云受控环境。具体地域和配置先验证，ECS+K3s仅候选。Compose可作开发辅助，不替代K8s验收。全球来源不要求多地域部署。

## 2. 工作负载布局

| 所属服务 | 运行单元提案 | 扩容依据 |
| --- | --- | --- |
| web/入口 | 独立入口与前端 | 请求延迟与并发；不接管领域事务 |
| ingestion | 有界调度/接收及抓取Worker | 每源积压、访问配额与网络上限 |
| processing | 解析Worker、必要时受控Job | CPU/内存、文件大小、队列年龄 |
| catalog | 查询API与索引/事件Worker | 查询延迟、索引滞后、数据库能力 |
| workspace | 权限/档案API及relay | 授权可用性，不以旧缓存放松安全 |
| research | 接受/查询API与AgentWorker | 可执行任务、模型配额、预算与等待 |
| tracking | 决定/关注/提醒API、复核与定时Worker | 变化扇出、临期任务、去重 |

一服务可有多个运行单元，不据此增加业务微服务计数。初期不默认每服务多个web worker/副本；定时入口提交持久幂等任务，不把状态只存在Pod内存。

## 3. 低预算运行与资源账

月总预算约100–200元，详见16。一个PostgreSQL实例按服务分库/角色；redis-core与redis-cache为两个独立进程，前者事件/配额不可淘汰且有持久与重放策略，后者可淘汰可重建。共用物理机是成本折中，不是高可用。

资源账必须计OS/K3s、PostgreSQL/连接池、两个Redis、实际API/Worker、解析峰值、向量索引、观测、镜像及备份临时空间，留峰值余量。4核8G/16G只是比较档，不由最低集群要求推导能跑全部业务。

不在在线小机器构建所有镜像。解析、索引、批处理错峰限并发；观测保留关键指标/trace关联/短日志和告警，不强制同机堆完整重型平台。调整保留期与采样不能删除必要业务证据。

独立备份不能只在同盘。原件/制品/索引/日志/备份分别计量与保留；持久卷不是备份，AOF不是事件业务恢复的替代。

## 4. 每服务部署契约

独立依赖锁、镜像digest、配置、身份、迁移、Deployment/Service、requests/limits、startup/readiness/liveness、优雅退出与日志关联。

liveness不因外部网站/模型暂时失败无限重启；readiness按是否可安全接新任务定义。Worker退出先停止领取，再完成或让租约接管；超时任务不能要求无限等待。

禁止默认privileged、主机管理socket、共享所有密钥、公开DB/Redis或集群管理面。兼容性允许时使用最小权限和只读根文件系统，必须实际验证。

公网只暴露必要业务入口，私有下载校验当前授权。密钥不进Git/镜像/日志，云权限和源/模型凭据按服务最小范围分配。

## 5. 网络与身份

选择真正支持NetworkPolicy的CNI，默认拒绝后开放必要DNS、服务、数据与获准出口，并实际测试允许和拒绝连接。[S22](12-source-register.md#s22)

网络允许不是业务授权；调用验证服务身份、issuer/audience/有效期，以及用户或后台委托。ServiceAccount名字本身不等于HTTP鉴权，不强制上服务网格。

ingestion是受控网页出口；processing不持有模型Key或任意公网权限；research只访问批准模型和服务API。URL/DNS/IP/重定向/元数据地址防护另在采集器实现，NetworkPolicy不代替SSRF校验。

## 6. 发布与可重建环境

Terraform为基础资源描述候选，Helm/Kustomize为应用部署二选一；具体版本与认证方式实现前审核。文档变更不触发付费部署，不可信PR不带密钥；真实源/模型检查手动且限额。

每服务可单独执行静态检查、单元/集成/契约测试、镜像构建/扫描和发布。schema按expand→迁移→contract，验证N/N-1兼容；回滚旧镜像不自动撤销破坏性迁移。每次发布有数据与业务恢复说明。

演练单服务升级和回滚，其他服务仍能提供约定的有限能力。原地一次部署成功不等于独立演进已验证。

## 7. 先测基线，再逐级加压

| 档位 | 数据规模候选 | 压力候选 | 用途 |
| --- | --- | --- | --- |
| L0 | 1,000条目录记录或实际更小种子 | 10虚拟用户、1–2模拟分析并行 | 基础行为和状态恢复 |
| L1 | 10,000条 | 25虚拟用户、2–5模拟并行 | 查询、索引、缓存与积压 |
| L2 | 100,000条 | 100虚拟用户、10–20模拟并行 | 仅资源/预算允许时验证瓶颈 |
| L3 | 1,000,000条 | 另行设计 | 条件扩展，不是v1完成条件 |

这些是实验输入，不是容量承诺；记录/文档/块分开计，扩增标amplified_replay。虚拟用户不等于RPS或真实活跃用户。也可另做固定到达率10→50→100请求/秒实验，但要独立报告完成吞吐、拒绝、超时和排队，不混用口径。

三轨分开：查询看P50/P95/P99、冷暖缓存、DB连接/慢查询；数据看文件格式/大小/页数、docs/min、MB/min、内存和隔离；研究用模拟429、超时、流式和坏JSON验证平台，小批真实模型另测质量与费用。

高压只对自有/获准环境，不压政府网站或无限消耗真实模型。候选预热、稳态和持续时长需事先批准，短样本分位数不宣称稳定SLA。

## 8. 扩容与停止规则

先比较固定1→2→4副本，再研究HPA；看吞吐是否增长及瓶颈转移，不假设线性收益。[S21](12-source-register.md#s21) parsing看CPU/内存与积压，research看队列、可用模型配额和成本，不能仅凭CPU加Worker。

计算pool_size×副本数与数据库可用连接；最大副本受DB、Redis、对象存储、源/模型总配额和预算约束。配额服务不可用暂停相应外部调用，不让每个Pod各享完整额度。HPA增Pod不等于可以自动买节点。

scale-down有稳定窗口与drain。费用预留不足、持续OOM、磁盘不足、事件日志逼近保留窗、权限异常或外部限流恶化时停止升压，保留证据并恢复。

正确性先于好看的数字。429/背压是保护行为但仍报告比例，不从总分母移除不利结果。性能目标在真实L0基线后冻结，不预写已达延迟。

## 9. 故障与恢复

覆盖Pod中止、parser OOM、大文件超时、Redis重启/已发送事件丢失、消费组重建、DB短时不可用、错误网络规则、模型429、授权服务不可用、取消/提交并发、单服务兼容升级及备份还原。

每次写预期、注入范围、停止条件、实际状态/日志/指标、恢复步骤和未覆盖项。跨服务恢复需对账版本、孤立引用、撤回和重复提醒；看到数据库启动不等于业务恢复。

多节点实验需另行批准资源和存储方案；单机多个虚拟节点不证明物理主机高可用。控制面、Worker、存储和DB分别有故障域，不能用Pod重启代替整机灾难恢复。
