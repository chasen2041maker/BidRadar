# 02｜产品范围与业务契约 v0.3

**Proposed｜2026-09-11。少源起步、项目优先已确认；具体页面、角色和行为仍待审核。**

## 1. 用户和非目标

软件/AI 服务团队的业务人员找项目，技术人员核查能力，负责人确认档案。首版允许一个用户维护一个工作空间；仍用两个测试空间验证隔离，不为只有一个实际使用者省掉权限。

不假设任何用户具备特定国家实体、认证或当地交付能力。系统给初筛依据，不认证法律资格，不自动报价、投标或联系采购方，不扩成完整 CRM。

## 2. 业务对象

| 对象 | 含义 |
| --- | --- |
| Notice / Procedure / Lot | 公告、采购程序、标段分别建模；一次发布不必然是新机会 |
| Document version / Evidence | 不可变原文与解析版本、定位、作用范围和访问条件 |
| Company profile | 经用户确认的能力、资质证据和偏好版本 |
| Analysis | 固定输入下的条件判断、引用、未决项和报告 |
| Review decision | 人工待核查/跟进/放弃及理由，不是模型资格判定 |
| Watch / Notification | 跟踪开关、变化规则、复核结果和应用内提醒 |

这是内部模型，不宣称所有来源都有这些原生字段。Review decision 由 tracking 拥有；报告/提问由 research 拥有；确认档案由 workspace 拥有。详见 [17](17-product-delivery-blueprint.md)。

## 3. 用户故事

| ID | 用户行为 | 交付与失败边界 |
| --- | --- | --- |
| U1 | 建立企业档案 | 人工确认、版本、有效期；未确认信息不覆盖事实 |
| U2 | 找值得看项目 | 相关列表、状态/日期类型、范围和同步时间；源失败不伪造空列表 |
| U3 | 核查条件 | 要求—原文—能力—五状态—待补材料；附件不全不得称全部检查 |
| U4 | 在项目内追问 | 保留标段、版本、未决问题和历史；超范围先明确切换 |
| U5 | 决定是否继续 | 保存人工决定与理由，支持修改；不以此证明投标资格 |
| U6 | 收藏并跟踪 | 版本变化、影响解释、复核和提醒；停止跟踪是显式动作 |
| U7 | 纠正档案或指出错误 | 区分偏好、能力事实、官方数据、模型判断；生成新版本不改旧原文 |
| U8 | 了解任务与数据状态 | 排队/运行/部分完成/失败/取消/预算暂停；适当角色查看诊断 |

R1 包含 U1–U5 的首次闭环和 U8 的必要状态；R2 增加持续跟踪与完整纠错。不能只做一个聊天页面替代这些行为。

## 4. 页面职责

企业档案页确认事实与偏好；商机列表展示匹配理由、状态与覆盖；详情/研究页用同一项目上下文展示条件、原文、追问和进度；跟踪中心保存人工决定、关注、变化与已读；数据/任务健康页给管理员查看失败、隔离、积压与成本。

这些是职责不是必须同时开发多个独立应用。首个版本可以合并详情和研究面板，不强做全球地图、复杂仪表盘或精致首页。

页面不把“任务运行成功”显示成“所有条件满足”；报告已完成但旧输入已变化时显示陈旧，重新分析由明确动作或获授权跟踪规则触发。

## 5. 数据范围

建议 1 个有用主来源先完成闭环，第二来源按证据或覆盖缺口加入。取消 R1 四源、R3 六源及三活跃来源门槛；未覆盖地区如实说明。

完整 v1 保留真实 HTML 和文件输入清洗，但可以由同一发布者提供，也可以在核心研究可用后补齐。格式不同不算不同来源。历史/负例不进入当前机会清单，全球扩源不阻塞 v1。

首个语义分析版本建议限定已人工核验的语言；原文留存、索引、翻译与条件理解分别声明支持级别，翻译引用回原文。

## 6. 判断形式

条件状态沿用 met/unmet/unknown/conflicting/not_applicable；总体给值得核查、明确冲突或资料待补充，不给中标概率。硬条件、偏好和相关性分开。

禁止：没填资质就当不具备、没写驻场就当远程、预算缺失就填零、只有公告就说完整标书已审、源失败就说没有新商机。

## 7. 跟踪与反馈

人工决定和 watch.enabled 独立；放弃时可询问或显式选择是否停止跟踪，不静默改变。已生成提醒/历史报告不因停止跟踪删除；未完成复核在执行新调用前重新检查委托与取消。

只在日期类型、作用范围和时区可确定时做精确临期提醒。实质变化触发必要复核，排版变化只记录。第一渠道应用内，外部邮件另审。

用户纠错保存类型、原判断、证据、操作者和处理状态；个人反馈不是自动真值，也不直接用作训练标签。自然变化与回放分开标注。

## 8. 使用者验证

拟找 2–3 位潜在使用者，或先明确标为自用验证；数量不是已有用户。让其完成一次核查和一次继续使用，而不是只看演示。记录看到的报告、修改内容、实际决定、遗漏、用时和是否回访。

没有外部使用者时不虚构商业价值；无法获得完整资料时降低结论范围，而非放弃来源说明或用模型补造。更多验收见 [08](08-evaluation-acceptance.md) 和 [17](17-product-delivery-blueprint.md)。
