## 2. 哪一段属于 RAG

RAG（检索增强生成）的核心是先获取相关外部资料，再让模型基于这些资料生成回答；不是“给模型取一个招标专家角色”就让它凭训练记忆回答。[S1][S2]

在 BidRadar 中，RAG 主要用于条件分析和项目内追问；分析还包含确定性核对和可追溯结果保存。[06](06-agent-memory-matching.md) 已把权限、规则、检索、语义匹配和引用核验分开。

| 已确认流程 | 拟承担的能力 | 与RAG的关系 |
| --- | --- | --- |
| 确认企业档案 | workspace保存人工确认的能力、证明、限制和版本 | 不是RAG；分析时按权限读取它 |
| 找到真实相关项目 | ingestion/processing准备资料，catalog过滤与检索候选 | 检索本身不是完整RAG；生成有据推荐理由时可以使用RAG |
| 查看实际材料 | 原件、附件可得性、版本与定位 | 是证据基础，不等于已完成检索或分析 |
| 生成引用与未知项分析 | research检索条款、语义解释、规则比较、引用核验 | 核心RAG用途，但不能省掉业务校验 |
| 同项目追问一次 | 带当前问题与有限上下文，检索冻结版本内相关证据 | 典型RAG用途；需重新校验当前访问权限 |
| 保存人工跟进/放弃 | tracking保存用户决定、理由、版本与幂等 | 数据库/业务状态，不由模型擅自写入结论 |

此表沿用六服务职责作为设计参照，不因此冻结六服务最终边界，也不把每一行等同于一个Agent。

## 3. 两种检索不要混成一个大知识库

发现阶段是在允许的公共项目目录中找候选；研究阶段是在当前项目/标段、已知材料版本和授权范围内找支持结论的证据。企业私有资料不混进公共索引；其他项目的条款不能因相似度高而当作本项目要求。

建议第一版先有固定流程基线：当前授权/版本过滤→检索证据→构造问题和必要企业事实→生成解释→核验引用、范围和已知数字→保存报告。短材料可先完整读取作对照；大材料按结构检索，但必须报告实际覆盖和缺口。

RAG不等于必须单独部署向量数据库。检索可来自既有SQL/文档库或检索工具；关键词、结构过滤、向量/混合检索如何组合，应看真实样本结果再定。[S2][S3] 数据库保存事实，检索索引帮助找资料，Redis缓存可重建结果，三者不能互相替代。

## 4. Agent 可以增加什么

固定RAG通常先检索再生成；Agentic RAG让模型在受控工具内决定何时以及如何补充检索。[S2][S4] 例如发现正文引用附件而该附件未在当前材料内，可提出获准补证请求；拿不到就记录未知，而不是自行上任意网站找一份相似材料。

建议先单一研究编排和确定性节点，允许的补证需要版本记录、时间/调用/费用上限。是否引入更灵活编排、具体模型与框架待评测，不因“Agent”名称就必须多Agent，也不以换框架替代证据质量。

## 5. 虚构走查：未知不能被检索掩盖

仅作说明的虚构材料：标段A正文要求“与现有工单系统对接”，并把接口规范指向一个尚未取得的附件；演示企业档案只有“做过API集成”的确认记录。

可支持的回答是“有工单对接要求”，附正文版本和条款定位。不能据此宣布“本公司肯定能交付”：具体认证方式、接口限制和工作量还未知，需补附件。另一个项目写“无需对接”不能用于本项目。

最少走查四类失败：正确条款未被检索到；材料版本/标段串用；引用能打开但不支持结论；企业证明或附件缺失。未检索到不等于不存在，带引用不自动等于正确，模型回答流畅不代表范围覆盖充分。这些是拟验收项，不是本轮测试成绩。

## 6. 本轮没有锁定的事项

Python/FastAPI、TypeScript/React、PostgreSQL继续作为现有主栈提案；具体六服务边界、模型、检索参数、鉴权和部署规格未冻结。Strapi继续先做中文流程与资源验证；CMS只管理平台原创内容，不接管招标原件。微服务、早期Redis/K8s、总预算及中文注释/学习规则不变。

本轮仅确认并记录产品范围、解释技术分工。没有搜索或导入真实商机，没有执行RAG/模型/CMS/缓存集成，更没有采购、部署或常态合并授权。首家试用者、具体首来源和实施验收仍需证据；已经确认的市场/目标用户/闭环不再反复要求拍板。
