# 19｜管理后台、开源 CMS 与缓存

**2026-09-12｜DESIGN_REVIEW｜需求已确认，具体技术方案 Proposed，尚未实现。**

读取基线：main `507a01ecc0c473a93b720012eb75a753cc4bafdd`。本页承接负责人认可的两类后台及五类功能范围，以及新增的“复用成熟 GitHub 开源 CMS”“缓存也要做”。不扩大为完整 CRM，不改变软件/AI 服务团队的目标用户，不假设团队必须能驻场。需求与决策见 [11 第 8 节](11-decision-register.md#8-后台cms-与缓存补充2026-09-12)。

## 1. 两类入口与五类后台功能

企业工作台服务本企业的档案、成员、商机、研究与跟进；平台后台服务 BidRadar 的运营。可在同一网站划分入口与权限，不预先创建两套用户系统或两套独立前端应用。

| 平台后台范围 | 用户动作 | 数据与执行责任 |
| --- | --- | --- |
| 公告与材料 | 查看原文、缺失材料、质量隔离；提交或审核纠错 | ingestion / processing / catalog；原件不可覆盖，纠错生成新版本 |
| 来源与任务 | 查看同步/解析/研究任务及失败原因；受控重试、暂停或取消 | 各任务所属服务；重复操作幂等，不把入队当完成 |
| 用户与权限 | 必要的账号/空间状态与角色管理 | workspace 维护企业授权；平台操作不默认授予私有内容访问 |
| 平台内容 | 帮助文章、常见问题、站内公告的编辑、草稿、发布、撤下 | CMS；这是复用开源项目的首要范围 |
| 费用与操作记录 | 查看可见用量、限额状态和关键操作记录 | 各服务保存自己的事实与审计，后台经受控 API 汇总 |

后台页面不是数据所有者，也不是直接修改所有数据库的超级工具。隐藏按钮不能代替服务端授权。企业成员不能进入平台编辑后台；CMS 编辑员不能因此获得企业资质、私有报告、费用策略或任务重试权限。

## 2. 选型：推荐 Strapi 5 Community Edition

上游：[strapi/strapi](https://github.com/strapi/strapi)。优先采用官方发行包与自有薄配置/扩展，不复制整个上游源码，也不引入来源不明的二次打包系统。

本轮核验日为 2026-09-12：官方发布页显示 v5.53.0 于 2026-09-09 发布，近期仍有连续发行与修复；官方文档提供内容建模、编辑后台、REST API、草稿发布、媒体管理和管理员 RBAC。[S1][S2][S4][S5] 这能支持选型，不代表已完成本项目的安全评估或低预算性能验证。

| 候选 | 本轮已读官方依据 | 本项目取舍 |
| --- | --- | --- |
| Strapi | 自托管、JS/TS、内容 API、PostgreSQL、可扩展后台；社区版 MIT，企业部分另有许可 | 推荐独立内容后端，不要求改写 Python 业务服务或先选定 Next.js |
| Payload | MIT、TypeScript、Next.js 原生后台，版本与草稿、细粒度访问控制 | 可行备选；当前未选 Next.js，暂不为内容模块增加前端框架绑定 |
| Directus | 当前官方许可证页为 MSCL-1.0-GPL，有使用限制及未来 GPL 转换条款 | 不作为本轮优先项；不能沿用旧文章把当前版笼统当作无条件 MIT 类开源 |

依据：[S1]–[S8]。表中取舍是本项目的工程判断，不是完整性能横评。

**社区版边界：**基础内容与 RBAC、Draft & Publish 可复用；官方 Audit Logs 属 Enterprise，Content History 属 Growth/Enterprise，不能算作免费现成功能。[S4]–[S7] BidRadar 的关键业务审计继续由业务服务实现；CMS 发布/撤下的必要操作记录与发布快照属于需实现的薄扩展，不冒充企业审计套件或完整内容历史。若这部分成本不可接受，再回到 Payload 比较，不绕过许可证。

使用时保留适用的版权与许可声明；社区版、企业代码、云服务与插件许可分别核对。[S3] 正式接入前锁定确切依赖和运行时版本、复核安全公告，不使用浮动 latest 作为可复现交付。不开启额外 AI、MCP 写入、外部邮件或付费插件。

## 3. 接到哪里，不接管什么

推荐边界是：内容编辑入口 → Strapi → 独立 cms_db；已发布内容通过内容读取接口进入用户工作台。业务管理入口 → 现有网关 → 拥有该业务的服务。两类入口可以互相导航，但身份、会话与授权不得直接等同。

CMS 是六个业务域之外的内容支撑组件，不替代 workspace、catalog 或 research。可与其他数据库共用 PostgreSQL 实例，但只使用 cms_db 的独立凭据、迁移和备份；不跨库读写，不用 CMS 自动建模重建全部业务表。共机不是高可用，新增 Node.js 进程与连接数需要计入资源账。

首批 CMS 内容仅限平台原创帮助、常见问题和站内公告；“站内公告”不等于采购公告。外部原文、更正链、证据、企业能力与模型结论继续由原服务保存。私有企业附件不能进入公共媒体库。富文本、媒体类型、大小、资源访问和上传权限仍需安全校验。

原始公告写错日期与解析器读错日期必须分开：前者是上游资料变更，后者是系统纠错。后台纠错生成新的派生版本，旧报告保留并标记待复核，不直接改原件隐藏错误。

## 4. 缓存对象与失效边界

目标是减少重复读取，而不是把 Redis 变成事实数据库。按 cache-aside 设计：校验请求与权限，尝试缓存；未命中时向数据拥有者读取，缓存可重建结果；变更先提交事实，再触发失效。[S9] 每个拥有者负责自己的缓存空间，不借缓存绕开服务接口。

| 对象 | 初步策略 | 必须保持的边界 |
| --- | --- | --- |
| 已发布帮助/平台公告 | 缓存正文，键带环境、语言、内容 ID、发布版本；发布/修改/撤下使旧查询失效 | 草稿与预览不进入公开缓存；读取当前页面仍核对有效发布状态，撤下不能只等长 TTL |
| 公共商机列表与详情 | 缓存标准化查询和固定版本详情；键带筛选、分页、语言、目录版本；显示同步时间 | 公共列表与企业个性化排序分开；来源失败不能缓存成“没有项目” |
| 企业档案快照 | 对确认版本作短期私有缓存，命名空间包含 workspace、对象/版本与必要访问范围 | 命中后仍执行当前授权；角色或成员撤回不能等缓存过期后才生效 |
| 研究结果 | 首先读取持久化报告；只对同空间、同项目/标段、同输入与配置版本作精确复用 | 刷新页面不重跑模型；新输入不能命中旧报告并冒充最新；不做跨企业语义答案缓存 |
| 解析与检索制品 | 按内容摘要、解析器/分块/索引版本和可见性复用 | 公共、私有制品分区；证据需要回核正确版本和当前访问权 |

示例键只是设计示意：`br:{env}:cms:published:{content_id}:{locale}:{revision}`。私有键还需 workspace 与访问范围，且键命名不是权限控制本身。不把密钥、原始提示词或私有正文塞进键名/指标标签。

**变更一致性：**失效事件可能丢失或乱序，也可能发生旧请求晚回填。设计采用拥有者的不可变版本键、单调版本/代次检查及可重试失效记录；旧读取不能覆盖新版本指针。TTL 是兜底，不承诺靠“删一次缓存”实现强一致。最新状态、撤下、撤权等敏感判断回到当前权威状态核验；无法核验时不继续返回受限内容。具体事件和接口在实施前补入 14，不在本页创造新事件枚举。

**故障与防护：**缓存故障时，允许的数据读取走短超时、并发上限和熔断保护的回源路径；上游也失败则返回明确不可用，不能无限重试。授权失败或费用/配额服务失败不能借缓存降级绕过。输入校验、短期合法不存在结果缓存、TTL 分散和同键请求合并用于验证穿透、集中失效和热点重建；锁只优化重复读取，不代替任务/计费的数据库幂等约束。[S9]

## 5. Redis 两种责任与验收

保留 04/07 的两进程设计：redis-core 负责事件及受限配额，采用 noeviction、持久化和数据库恢复依据；redis-cache 保存可淘汰副本，配置独立 maxmemory 与淘汰策略。不是同一进程换两个逻辑 DB 编号。Redis 官方说明 noeviction 在超限时会拒绝相关写入，也建议混合持久数据与缓存时考虑分实例。[S10] 应测试背压与恢复，不把持久化等同于零丢失。

TTL、容量、锁时限与延迟目标要由本项目实测确定，不编造命中率或吞吐量。至少保留命中/未命中、回源次数、失效延迟、过期/淘汰、内存、错误率和端到端延迟；指标不得使用高基数企业标识或私有内容。

| 验收场景 | 需要观察到的结果 |
| --- | --- |
| 同一已发布内容重复读取 | 正文可命中，减少相应回源，读取结果正确 |
| 修改/撤下与旧请求晚回填 | 当前页面不被旧值覆盖；撤下不从旧缓存复活 |
| 空结果、来源失败、解析失败 | 不把失败混成真实不存在，不隐藏材料缺口 |
| 两个空间、撤权、旧会话 | 即使缓存有值也拒绝越权；不串企业资料 |
| 同时失效或热点请求 | 记录回源并发与合并效果，不拖垮数据拥有者 |
| redis-cache 不可用 | 受限回源或明确失败；不绕过鉴权、配额和费用限制 |
| 相同报告重复打开、新版材料到达 | 前者不重复调用模型；后者保留历史并明确需要新分析 |

这些是验收设计，不是已通过测试。

## 6. 对既有计划的增量与下一小步

本页补充 01/02/17 的后台产品范围、03/04 的内容与数据所有权、07/08 的缓存失败验收，以及 09/15/16 的阶段与资源考虑；未改动的既有专题继续有效。六业务域、少源起步、Redis/K8s 早期纳入与预算上限不变。

D0 当前只完成选型与范围记录。未来实施时，CMS 首条小流程可独立验证，但不能要求先完成五类后台才允许 R0/R1 的招标研究主线推进；业务任务页随所属服务进入 R0/R1，持续跟踪和完整运营验证随 R2/R3 进入。实际工时仍待确认，不把此前 28 周容量提案自动延长或冒充承诺。

CMS 进程、数据库连接、媒体、备份与缓存都计入原 100–200 元/月总预算。没有新增采购或预算；本轮未重查云报价、未验证共机容量。后台与正文缓存不是免费资源，也不靠取消权限或恢复来压成本。

**下一项只细化“帮助文章发布与缓存”这一条流程：**

- 用户行为：编辑一篇帮助文章，发布后在工作台读取，修改后更新，撤下后不再公开。
- 知识点：开源项目配置边界、内容状态、服务端权限、cache-aside、版本与失效。
- 输入/输出：明确标演示的文章及编辑/读取身份；输出已发布正文、当前发布状态与可观察的缓存命中/失效记录。
- 失败场景：草稿泄露、无权发布、撤下后旧值复活、缓存故障、重复发布动作。
- 实现范围：只做内容类型、必要权限、正文读取/缓存薄适配与测试；不代写整个 CMS，不接模型、真实采购采集或全部运营模块。
- 验收：上述发布/更新/撤下和负例有可复查结果，并记录运行资源。具体编码任务在讨论清楚后推进；本次不安装依赖或启动服务。
