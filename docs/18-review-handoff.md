## 2. 为什么做，以及不能丢掉的背景

项目面向软件与 AI 服务团队，帮助判断公开招标项目是否值得继续核查：发现项目、读懂要求、比较企业能力、保留证据与未知项，并跟踪变化。

负责人希望独立承担真实数据获取、清洗、Agent 编排、记忆、数据库、测试和部署全过程，以实际作品证明多家公司 Agent／AI 应用工程岗位所需能力。已有公司投研项目只参与部分功能，且公司数据不可取得；不能当作个人完整作品，也不使用公司代码、数据、账号或内部资料。

投研方向、普通客服/工单方向、Agent 测试开发者工具方向已在选题阶段排除。当前审核对象是 BidRadar，不重新开始一轮选题，也不把项目改成只采集公告或只做摘要的工具。

## 4. 仍是提案，不要替负责人接受

六服务划分为 ingestion、processing、catalog、workspace、research、tracking；Python/FastAPI、LangGraph、PostgreSQL/pgvector、Redis Streams、Outbox/Inbox/事件重放是当前设计中的候选和细节，具体边界与协议仍需审查。微服务数量不等于 Agent 数量。

首来源未通过准入；“1 个主来源，按需第 2 个”是实施提案，不是已接通成果。具体模型、认证方案、API/事件字段、质量阈值和语言支持均未冻结。

阿里云 ECS+K3s 单节点、4核8G/16G、按服务分库和两个 Redis 进程是低负载方案提案，不是已核实报价或资源足够的保证。单机多服务不等于多节点高可用；预算不等于采购授权或厂商账单硬封顶。

28 个有效项目周、每周12–15小时是容量估计，实际工时、开始日期和最终排期未确认。完整交付中保留评测、故障恢复和英文交接，不因扩源挤掉它们。

状态与替代关系以 [11 决策登记](11-decision-register.md) 为准；旧技术专题的编制日期不自动表示它被整体废弃，也不允许旧来源数量门槛覆盖最新要求。

## 5. 阅读顺序与审核重点

先读 [AGENTS](../AGENTS.md)、[README](../README.md)、[01 计划书](01-project-plan.md)、[17 产品蓝图](17-product-delivery-blueprint.md)、[11 决策登记](11-decision-register.md)，建立产品、授权和事实边界。

再按 [00 审核指南](00-review-guide.md) 读取产品/Agent/评测、架构/领域/事件/可靠性、数据/排期/容量/预算专题。不要只看 README，也不要为了理解产品先扩充全球来源名单。

当前需重点核查的不是已证实的线上故障，而是设计是否能回答：

1. 第一来源是否有足够相关、可定位的材料，支撑条件分析、追问和变化复核？
2. 服务所有权和人工决定/跟踪状态是否一致，哪里还需要补充契约？
3. 重复、乱序、消息丢失、旧 Worker、取消和撤权时，如何避免重复发布、过期结果和私有泄露？
4. 六服务和数据库/Redis/观测能否在总预算内运行？没有实际报价和负载时，不能提前认定可行或不可行。
5. Agent 相比人工/规则基线是否有可测价值，任务是否由本人掌握，而不只是 AI 生成的目录和文档？

## 6. 审核报告要求

报告开头给出读取的分支/SHA、实际阅读范围和阶段判断。把确定的文档矛盾、设计风险、待验证假设和已通过实测分开；当前不得写出不存在的通过成绩。

每个问题给出文件路径与章节、触发场景、影响、优先级、最小修改和验证方法。P0/P1 等风险级别需定义，不与产品 P0/P1 功能优先级混用。不为凑数猜问题，不要求为了所有 JD 关键词增加框架。

可提出技术取舍和可行性异议，但不得自动改代码、提交、开工、买资源或改变已确认方向。无法取得某文件就注明未审，不从标题推测正文。

完整个人简历、联系方式、私人薪资目标、公司资料、账号凭据和账单不放入公开仓库。需要结合求职背景审核时，由负责人在新对话私下补充；不能凭文档有某项技术就认定本人已经熟练。

[10 JD 对照](10-jd-alignment.md)、[12 来源登记](12-source-register.md)和16中的外部资料带历史核验日期。本轮交接未重新核实招聘、数据源或云报价。若审核需要当前事实，应另行核验并区分官方证据、历史记录和设计建议。
