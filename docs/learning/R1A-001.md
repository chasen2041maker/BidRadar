## 阅读顺序

只按这三个核心文件阅读，中文注释围绕边界和原因展开：

1. [http_api.py](../../services/workspace/http_api.py)：`Handler._dispatch`。先看会话绑定和`current_member`，再看`selections`分支：旧命令重放 → catalog核对固定ID → 私库写入。理解为什么服务间只传契约，不读取对方数据库。
2. [store.py](../../services/workspace/store.py)：`_transaction`、`_authorize` → `confirm_profile` → `replay_selection`、`_transition_selection` → `change_member`。重点是事务里重验当前会话/成员、乐观版本比较、幂等结果与业务状态同事务保存，失败一起回滚。
3. [app.js](../../services/workspace/web/app.js)：`command` → `switchWorkspace`、`api` → `loadProfile`、`loadSelections`。理解浏览器如何保留重试键，如何立即清空旧公司DOM并丢弃迟到响应，以及“已选定·尚未分析”为何必须分开显示。

需要深挖服务间限制时，再从HTTP入口跳转`CatalogClient.validate_selection`：单次请求5秒，整个选择核验15秒，响应大小有界，拒绝重定向和任意来源URL。主线不用先读所有测试或启动脚手架。

## 数据流与失败边界

页面提交会话Cookie、CSRF、当前公司、正式档案版本和公告固定ID → workspace检查Origin/Host及当前授权 → catalog返回公共证据快照 → workspace在写事务中再次检查身份/成员/档案版本 → 原子保存私有选择及幂等结果 → 页面展示待确认 → 人明确确认才转selected。查看和刷新只读取已有结果，全程没有模型调用。

例如：管理员甲打开成员第1版；管理员乙先撤权生成第2版。甲随后保存旧页面，即使携带active=true，也因expected_version=1返回409，不能把成员重新激活。`test_stale_member_screen_cannot_restore_revoked_access`覆盖真实HTTP，存储测试同时检查不可改写的成员事件。

另一失败边界是catalog调用期间被撤权/注销：HTTP初检成功不足以放行，写事务必须再次拒绝；迟到读取也重验。成功创建后响应丢失则不同：当前仍有权限、同人同输入同键应直接返回已保存结果，不因catalog后来宕机而变成失败。档案更新不会改写旧选择，新确认必须主动解决版本冲突。
